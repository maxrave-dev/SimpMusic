# Now Playing

Notes on the Now Playing shell and its three styles (Classic, M3 Expressive, Apple Music), animated artwork and canvas, video frames and the comments sheet. Moved from the changelog in `CLAUDE.md`; each entry keeps its original date. Add to this file by the Auto-Update Rule in `CLAUDE.md`.

- **Now Playing style system + Material 3 Expressive style (2026-08-23)**: the player is now a style-agnostic SHELL + swappable CONTENT layer, picked by a Settings row (User interface, under Theme) persisting `NOW_PLAYING_STYLE` (`SPOTIFY` default | `M3_EXPRESSIVE`; an Apple Music style is the planned third). `NowPlayingScreen.kt` went 2630 → ~670 lines and keeps everything style-agnostic — VM state collection, palette Animatables, artwork-pager sync, every sheet/dialog — handing the rest to the content composable through the two @Stable holders in `content/NowPlayingContentState.kt` (`NowPlayingContentState` / `NowPlayingContentActions`). The old UI moved VERBATIM into `content/NowPlayingContentSpotify.kt` (two sanctioned cleanups only: the twice-duplicated metadata row became `NowPlayingTrackInfoRow`, and `isUserLoggedIn()` — a `runBlocking` executed inside composition on every recomposition — became a shell-collected flow). The new style is `content/NowPlayingContentM3Expressive.kt` + `NowPlayingExpressiveCards.kt` + `content/expressive/{WavySeekBar,ExpressiveTransportRow}.kt`, built to the owner-approved "Tonal pills" design canvas.
  - **The one-screen vertical rule is per-style, not shell**: gap = max(30, (hDP − topBar − artwork − info − 30) / 2), artwork between two equal gaps, the inline lyric line centered in the lower gap, 30dp of breathing room before the fold — each content file carries its own copy of the measurement block, so a future style may define different maths without touching the shell.
  - **The expressive APIs are usable from commonMain on the pinned CMP artifact** (`material3-multiplatform 1.12.0-alpha01` = androidx 1.5.0-alpha19): `LinearWavyProgressIndicator` and `MaterialExpressiveTheme` carry `@Material3ExpressiveApi`, which is a `@RestrictTo` marker, NOT `@RequiresOptIn` — no opt-in needed; `MaterialTheme.motionScheme` is stable. The wavy seekbar is the *indicator* plus a transparent `pointerInput` layer (it is not a slider); the wave amplitude animates to 0 when paused OR while scrubbing, and the thumb morphs circle→tall bar during drag.
  - **M3E colours are a whole artwork-seeded dark scheme, not two gradient stops**: `rememberDynamicColorScheme(seed, isDark = true, style = PaletteStyle.Vibrant)` wrapped in `MaterialExpressiveTheme` around the content subtree, everything reading tonal roles (no `Color.White` semantics, no black-gradient `drawBehind`); falls back to the app `seed` until the artwork has been scored. The seed was `state.startColor` until 2026-10-03 (see that entry).
  - **M3E has no separate canvas-takeover UI, but the canvas itself renders FULLSCREEN at page level** (`NowPlayingExpressiveCards.kt:187-189`), behind the content — not inside the 28dp artwork card, and `cropToBounds` is not passed there (the modifier chain differs from the card's). Classic's video overlay (±5s seek, subtitles) is ported at that layer. Of the shell's `showControlLayout`/`controlLayoutAlpha`/`showHideMiddleLayout`, two of the three ARE used by this style (`NowPlayingContentM3Expressive.kt:187,:190,:258,:600`); only one goes unused. Transport keeps Classic's Android-only gate — the Desktop side panel still has no slider/transport in either style. *(Corrected 2026-08-24 against the ship commit: the entry previously claimed in-card rendering, `cropToBounds = true`, and all three fields unused.)*
  - The connected action group order is a product decision: Info · Output · Shuffle · Repeat · PlaylistAdd · Queue (Output replaced Cast on 2026-10-03). Design mocks must lift the real drawable, not the icon a name suggests — the old Cast slot was `ic_music_cast.xml` (Material Symbols `music_cast`) from the cast module, not Material "cast".

- **The Apple Music player's tabs broke three things that had been fine (2026-08-26)**: `Crossfade(targetState = viewState)` composes exactly ONE body, so on QUEUE or LYRICS the artwork pager inside MAIN does not exist — and the shell had been treating it as always alive. Tapping a queue row played the wrong song, and it took three attempts because the first two chased the symptom. The decisive clue was that **Classic and M3 Expressive are never affected** — they use `QueueBottomSheet`, which renders the WHOLE queue and passes the index `itemsIndexed` hands it, computing nothing. `AppleMusicQueueView` instead did `drop(offset)` and added `offset` back at click time, making every row's identity depend on `state.currentOrderIndex`, a value DERIVED in the shell. It now does `withIndex().drop(offset)` so the queue-wide index travels WITH its track: a wrong `currentOrderIndex` can still cut the list in the wrong place, but it can no longer play the wrong song. **When one screen is wrong and its twin is right, compare the mechanisms before debugging the values — the twin that computes nothing has nothing to get wrong.** Two further guards on the shell's pager→player effect: it is keyed on the pager alone with the index read through `rememberUpdatedState` (re-keying it per track rebuilt the `snapshotFlow`, whose first emission is the stale `settledPage` that `distinctUntilChanged` cannot suppress), and it now requires a latched `pendingUserSwipe` set by a real finger drag — on the Queue/Lyrics tabs the pager does not exist, so every seek it appears to request is fictitious. The page background went stale for the same reason (`onArtworkBitmap` is only fed from inside that pager), fixed with a loader outside the Crossfade. And the canvas flashed sideways on returning from LYRICS because `MediaPlayerView`'s legacy path seeds its width to the SCREEN width and only corrects it once `onVideoSizeChanged` reports the truth — `cropToBounds = true` takes its size from Media3's `presentationState` instead, so there is no wrong guess to correct.

- **Animated album artwork as a second canvas source (2026-08-31)**: an opt-in setting (**off** by default) that plays Apple Music's animated album cover in the slot a Spotify canvas fills. It reuses the AM plumbing that already existed for the artist name-logo — `AMTokenManager` scrapes the web-player JWT out of `music.apple.com/assets/index~*.js`, `buildAMHeaders` signs the call, and both search helpers carry the same refresh-once-on-401 retry — so **not one line of token handling was written for this**. The result is a plain `CanvasResult` persisted into the existing `song.canvasUrl` / `song.canvasThumbUrl` columns, which is why nothing downstream and no migration had to change.
  - **The two sources are one slot, so AM wins in code while both switches stay independent in the UI.** `SharedViewModel.getCanvas` picks the source with a `when`, and the Spotify switch is deliberately left alone — it stays where the user put it and simply stops being consulted. Racing them, or disabling the other switch, would both be wrong: the first spends a login-gated round trip per track on a result that gets discarded, the second edits a preference the user did not touch.
  - **AM's album index is not complete enough to trust a near-miss, so the album name is a first tier rather than the only path.** Searching "Mắt Nhắm Mắt Mở HIEUTHUHAI" with `types=albums` returns exactly ONE album — *Mắt Nhắm Mắt Mở (Studio Live Session) - EP* — and not the album itself, so the closest available match was a different recording entirely, accepted only because nothing else was on offer. `pickAlbumMatch` therefore accepts an **exact** name and nothing less; anything else defers to the track search, which finds the real album for the same track (`Đáng Lý Anh Nên Yêu Em Hơn` → *Mắt Nhắm Mắt Mở*, exact). The album name is still used on that path — as the tiebreak between the several albums a track legitimately appears on, ahead of "has artwork" and ahead of AM's ranking. Measured 12/12.
  - **A track title cannot be looked up as an album, and the failure is a silent empty result.** `types=albums` answers a title with the *singles* that share it — "Blinding Lights - Single", never "After Hours" — and those rarely carry animated artwork, so the request succeeds with 200 and the feature just never works. Measured 0/3 on the fallback path before this was found. The title path therefore searches `types=songs&include[songs]=albums&extend=editorialVideo`, which returns the parent album already extended, in the same one request. The album path keeps `types=albums`. (A single is not *disqualified* from having artwork — HIEUTHUHAI's "Người Im Lặng Gặp Người Hay Nói - Single" has one — it is simply rarer.)
  - **On the title path the album must come from the matched TRACK's `relationships.albums`, never from the flat `resources.albums` map.** That map holds every album any hit belongs to, so "the first album that has artwork" attaches an unrelated release to the song: for an artist with exactly one animated release, every one of their tracks wore it. Seen live on HIEUTHUHAI. `searchAMSongsWithAlbums` pairs each song with its own album and the caller scores the TRACK title.
  - **Running time is the strongest signal, and it was already the one the Spotify canvas search used.** That path picks its track by comparing durations, not names — the same idea applies here and is what separates takes a title cannot: "Không Thể Say" is 228s, its Live Band cut 188s, its festival cut 327s. `AMSongAttributes.durationInMillis` comes back in the same response, and `SongEntity.durationSeconds` is already on the row, so the song path demotes anything more than 3 seconds off before it considers the album name or whether artwork exists at all. Measured 12/12 end to end.
  - **Filter order decides correctness here: name closeness first, "has artwork" only as a tiebreak.** Filtering to albums-with-artwork *before* scoring discards the studio recording and leaves the live one, which then wins by default — "Không Thể Say" resolved to a festival live album. Scoring first and demoting artwork-less candidates within an equal-name tier keeps both cases right: a track that exists on a bare single AND on a full album picks the album (HIEUTHUHAI's "Nước Mắt Cá Sấu" → *Mắt Nhắm Mắt Mở*), while a track whose only exact match has no artwork correctly shows none. Measured 10/10.
  - **AM's ranking must never be the decision — it is only the tiebreak.** The search API cannot be told to sort, and its order is wrong in two different ways. It ranks a *different album* above the right one ("LINK Hoàng Thùy Linh" puts *Hoàng* **above** *LINK*, both carrying artwork), and it ranks **reissues above the plain edition** — *Hybrid Theory (Deluxe Edition)* above *Hybrid Theory*, *1989 (Taylor's Version) [Deluxe]* above *1989* — so taking the first loose match returns the artwork of the wrong pressing, silently and with no error anywhere. `pickMatch` requires the artist to agree, then scores each candidate by how closely its name answers the one searched for: exact, then subject-plus-a-suffix ordered by how much was added, then the looser containments. AM's own position is used only to break ties. Measured 10/11 exact against live responses at `limit = 5` — raising the limit changes nothing, so it stays at 5.
  - **Normalising to letters and digits can leave nothing at all.** Ed Sheeran's `÷` and `=` contain no alphanumerics, normalise to an empty string, and so matched nothing — those albums returned no artwork, again with no error. `matchKey()` falls back to the raw lowercased text for exactly that case.
  - **Normalising with `[^a-z0-9]` destroys the languages this app serves.** That class treats every accented letter as punctuation and grinds "Hoàng Thùy Linh" down to "ho ng th y linh"; the comparison is built on `Char.isLetterOrDigit()` instead.
  - **`isVideo = url.contains(".mp4")` had to widen to `.m3u8`.** AM artwork is an HLS master playlist, and the branch that reads this is the one restoring a *cached* url — so the mismatch would have rendered every AM artwork as a still image only from the **second** play of a track onwards. `Mapping.kt`'s copy is untouched: it converts Spotify's own response, where `.mp4` is correct.
  - Nothing in the player changed: `MediaPlayerView` builds a `DefaultMediaSourceFactory` and `media3-exoplayer-hls` was already a dependency, so ExoPlayer recognises `.m3u8` on its own, `REPEAT_MODE_ONE` already loops it, and mpv handles HLS natively on Desktop. The stream itself carries no auth, no DRM and no audio track, so it cannot collide with playback.
  - **The app picks the rendition, not the player — and codec is decided before quality.** `editorialVideo.video` is a MASTER playlist: one measured artwork advertises 28 variants, **16 of them HEVC Main 10 (10-bit)** interleaved with 12 H.264 by bitrate. mpv defaults to `--hls-bitrate=max` and so took the very top — `2048x2732` 10-bit HEVC at 20 Mbps, **52.39 MB for a 22-second loop**, decoded in software because canvas renders through mpv's SW render context — while ExoPlayer would have picked by bandwidth estimate, so the two platforms disagreed on the same track. `selectAMRendition` now resolves the master down to one media playlist before the url is ever stored: filter to `avc1`, take the narrowest rendition at or above 720 px, cheapest of those. Measured identical across six albums — `830x1106 @ ~2.85 Mbps` tall, `768x768 @ ~2.1 Mbps` square.
    - **Capping the bitrate instead does not work**, which is what the first attempt did. The ladder is generated per artwork, so one threshold lands on H.264 for one album and 10-bit HEVC for the next, and bitrate does not even track resolution within a ladder: `486x648` costs 1516 kbps while the larger `664x886` costs 1494. Filter by codec first, then by width.
    - Failure degrades rather than breaks: an unreachable or unparseable master falls back to the master url, which still plays.
  - The query is cleaned by the character-for-character same chain the canvas search uses. The setting sits in the **Spotify** section directly under the Canvas row, since it replaces what that row does — but unlike every other row there it carries **no `isEnable`**: those need a Spotify session and this one needs no account at all, so gating it on `spotifyLoggedIn` would hide it from the users it actually works for. Roughly a third of albums have no animated artwork, and those fall through to the still cover.

- **Now Playing video frames take the video's shape (2026-09-25)**: the frame around an inline video was a hard 16:9 in all three styles, so a 4:3 video sat pillarboxed and a vertical one shrank to a sliver. Every style now reads one value, `NowPlayingContentState.videoAspectRatio` (16:9 until known), and fits the frame into the space that style already reserves for artwork — never more, so the one-screen layout cannot grow. Spotify fits it inside the square slot; the hidden thumbnail under it takes the same shape while the video plays, because its box is what casts the artwork shadow — left at 16:9, that shadow ringed a tall video. M3E's card takes the video's shape inside a slot capped at square, and `expressiveCardSlotRatio()` is the ONE expression both the card and its measuring spacer use. Apple Music fits it into the zone above the controls, starting 16dp below the top chrome (status bar + 28dp grabber on Android, the glass dismiss button on Desktop), because the frame's top-right corner carries the fullscreen button. That zone is the page's own height minus the controls, NOT `artworkZoneHeightDp`: that value is measured against the window, and the Desktop side panel is shorter than the window by its shell padding, so a tall frame ran into the gap above the title.
  - The value comes from `rememberVideoAspectRatio(playerName)` (expect/actual). Android reads Media3's `rememberPresentationState(player).videoSizeDp`. Desktop reads mpv's `video-params/aspect`, observed by `MpvPlayer` and published as `MpvVideoFrameSource.aspectRatio` — the frames cannot say it themselves, since mpv letterboxes them to the target size. Living on the frame source, it is re-pointed by `MpvPlayerAdapter.currentVideoFrames` on every handle swap for free.
  - **The Full build's session player only reports what changed.** There `MAIN_PLAYER` is a Media3 `CastPlayer` (`ForwardingSimpleBasePlayer` → `SimpleBasePlayer`): it re-reads the wrapped player on `onEvents` and fires a callback only for fields that differ from its last snapshot. A view composed mid-video — Now Playing reopened after fullscreen — therefore never hears `onVideoSizeChanged`, `onTracksChanged` or `onMediaItemTransition` for the current item. `MediaPlayerViewWithSubtitle` started at `videoRatio = 16f / 9` and waited for that event, so the video came back stretched to 16:9 ever since Cast wrapping landed (core `c310577`, 2026-07-10); FOSS passes events straight through and healed on the next frame. UI state derived from the session player must be read from the player's getters (or Media3's `rememberPresentationState`) before listening.

- **Apple Music style: uncropped artwork, lyric strip, output capsule, mesh page (2026-09-30)**: MAIN was reworked. The controls block now hangs from the bottom of the page, and the artwork is a full-width **square** at the top (`minOf(width, height × 0.62)`), so a cover is no longer cropped by roughly a quarter of its width. The space left between the artwork and the title is page, not artwork.
  - **Apple Music's animated artwork is no longer a fullscreen canvas.** It plays in a frame of its own shape (3:4 or 1:1) at full width, top-aligned, with the controls exactly where the still cover put them — they must not jump when the clip arrives a few seconds in — so a tall clip's lower part fades out behind the title. The clip's still (`CanvasData.thumbUrl`, newly carried from `canvasThumbUrl`) sits under it, sizes the frame and fades out as the clip fades in. Only a **Spotify** canvas (`.mp4`, 9:16) still takes the whole page and auto-hides the controls; `isAnimatedArtwork()` tells them apart by the `.m3u8` Apple serves. Since 2026-10-03 the shell's auto-hide fires only for that canvas (`fullscreenCanvas()`). That canvas's bottom scrim is sized off the measured controls block (the controls fill its lower 60%), so the title sits at the same depth of the ramp however tall the block grows.
  - **The clip cannot be masked, so the page is laid over it.** Media3's `PlayerSurface` is used with `SURFACE_TYPE_SURFACE_VIEW` (`media3-ui/MediaPlayerView.kt`), and a SurfaceView is composited under the window: no Compose `alpha`, `DstIn` mask or offscreen layer reaches its pixels. Masked like the cover, the clip ended in a hard edge right under the title. Instead `AppleMusicMainView` draws a second `AppleMusicMeshBackdrop` — same mesh, same size, same seam, so it matches the page beneath it pixel for pixel — ABOVE the pager, faded in with `appleMusicFadeBetween` over the stretch the cover dissolves over, ending at the clip's bottom edge. Compose content drawn above a SurfaceView does cover it, which is what makes this work on every surface type; the frame itself carries no mask, so Desktop (where mpv frames are plain Compose images) gets the identical fade.
  - **The band under the status bar (Android)** is blurred and darkened so white status-bar glyphs and the grabber survive a bright sleeve. The owner rejected a first version (grabber + 40dp long, on a smoothstep ramp) as too dark and too long. The band is the status bar + 32dp. The blur is `TopBandBlur`: a `Modifier.blur(32.dp)` copy of the picture inside each pager page, solid under the status bar and gone at the band's end — the clip's band uses its still, since nothing blurs the video surface. The wash is black at `alpha × (1 − p)^1.5` (sampled at 24 stops), with alpha from 16% on a black sleeve to 65% on a white one, driven by `AppleMusicMesh.topLuminance` (the top grid row, read before lifting).
  - **The page is a mesh of the artwork's own colours** (`AppleMusicMeshBackdrop`): a 6×6 grid of means read bottom-up, rows below the seam shifted sideways by a seeded amount, smoothstep-resampled to 32×32 and drawn from the artwork's bottom edge (the first row is held above it), blurred 44dp, crossfaded 900ms on a skip. The colour directly under the artwork is the colour it ended on, so there is no seam to hide. LYRICS and QUEUE keep the frosted cover. Pixels are read through `toReadableBitmap()` (expect/actual) because Coil hands back HARDWARE bitmaps on Android, which throw when read or drawn into a software canvas.
  - **Every fade is smoothstep** — `appleMusicVerticalFadeEdges` now builds 24 stops on the curve `smoothScrimBrush` uses; the linear ramp it had left a visible line where the artwork started to dissolve. The owner asked for this twice.
  - **Lyric strip over the progress bar** (`AppleMusicLyricStrip`): the line being sung in `labelSmall` white — the role Classic and M3E use for their inline line — rising in over 340ms as the old one rises away. Word-synced lines are lit as they are sung by drawing the line twice and clipping the bright copy to the playhead in the draw phase, which is what lets the light travel inside a word. The playhead is the strip's own `rememberSweepPlayhead`, not LyricsView's `rememberSmoothPlayhead`: that one restarts from every 50 ms report, and since reports land a frame or two late and never on a frame, a continuous sweep stalled and jumped several times a second. The sweep clock runs on the frame clock, only leans toward the reports (time constant 150 ms), never runs backwards, and snaps only past 500 ms (a seek). Before the first line starts the slot holds three dots. One line tall in every state, so nothing below it moves. Tap opens the Lyrics tab.
  - **Text**: the main title row keeps M3E's roles (`titleMedium`/`bodyMedium`, 18/13sp) — one role up (`titleLarge`/`bodyLarge`, 25/18sp) was tried and rejected as far too big, since the app's scale jumps 18 → 25. Secondary text (artist, times, output caption, compact artist, queue subtitles) is `White @55%`, not `typo()`'s body colour: under `ForceDarkContent` that is an opaque `#A8A8A8`, darker than a bright sleeve's page, so it read as a dark grey smudge there. Both sliders' track is 8.4dp (16.8dp while held), 20% thicker than before.
  - **Quality line instead of the codec badge**: "154 kbps · 48 kHz" from the stream's own `NewFormatEntity.bitrate`/`sampleRate` (`toAudioQualityLabel`), behind a 13dp headphones glyph, pinned to the row's centre — the three-way weighted row wrapped it onto two lines. `audioCodecLabel` is gone.
  - **Dock → action row**: Lyrics · [Output | Listen Together] · Queue, with the output's name under it. The output half opens `AppleMusicOutputSheet` (the ⋯ sheet's card, handle and rows), where the device's own outputs and the **Cast receivers are one list** — Cast moved out of the dock into the sheet. The Listen Together half is highlighted while a room is live and navigates to its screen.
  - **Per-app output routing** — `MediaPlayerInterface.audioOutputs`/`selectAudioOutput`/`refreshAudioOutputs` (default: empty/no-op). Android: `AudioOutputRouter` lists outputs through `AudioManager` + `AudioDeviceCallback` and routes with `ExoPlayer.setPreferredAudioDevice` on every player (`createExoPlayerInstance` hands the pick to each new one). This routes the app's player only, not the phone. Picking what the system already uses clears the preference, so a headset plugged in later still wins. Desktop: mpv's `audio-device-list`/`audio-device`, applied to every live handle and re-applied in `applyPlaybackLevels`. **Only the pinned driver's devices are offered**: mpv lists every driver together, and naming a `coreaudio/…` device would switch a macOS handle back to the driver that crashes the process on hotplug (see "macOS desktop audio moved to `ao=avfoundation`" in `playback-desktop.md`). Cast receivers come from `rememberCastRoutes` in the `cast` module (MediaRouter with `CastContext.mergedSelector`; `selectRoute` starts the session and `unselect(UNSELECT_REASON_STOPPED)` ends it, per Google's "Custom Cast Dialogs"), with a no-op twin in `cast-empty`.

- **Classic and M3E play animated artwork the Apple Music style's way, and get the output sheet (2026-10-03)**: in these two styles Apple Music's animated artwork used to play like a Spotify canvas — page gone black, artwork card hidden, controls auto-hiding after 5 s. It now plays through `AppleMusicAnimatedArtworkPage` (in `NowPlayingContentAppleMusic.kt`, so it reuses that style's private pieces): the clip edge to edge at the top in a frame of its own shape, dissolving into a mesh of its own colours, with the controls where they always are and never hidden. It is the current pager page's top layer and covers the card once the clip's still is up; until then the style's own page stays in view, so nothing jumps from a square cover to a full-width one. Over its last 8% it fades into the colour below the fold (`PlayerBackdropColor`, M3E `surface`), so scrolling past it shows no seam. Only a Spotify canvas still fills the page.
  - `isAnimatedArtwork()` and `fullscreenCanvas()` live on the shared contract (`NowPlayingContentState.kt`). The shell's `showHideMiddleLayout` and every auto-hide trigger read `fullscreenCanvas()`, so animated artwork hides the controls in no style.
  - **The band under the top bar is taller than the Apple Music style's**, because the bar's title sits inside it: blur and wash are solid through the status bar and ease out by the bar's end + 32dp, the wash on smoothstep. The grabber's `(1 − p)^1.5` falloff would have left the title on a band that had already faded.
  - **Secondary text turns White @70% over animated artwork** (`secondaryTextColor()`: artist, elapsed, length). The mesh can be bright, and `typo()`'s body grey reads as a smudge there.
  - **Output replaced Cast** in Classic's bottom row and M3E's connected group: Headphones, opening `AudioOutputSheetHost` (the Apple Music style's output sheet, collecting its own state), where Cast receivers sit with the device's own outputs. Tinted cyan (Classic) / primary (M3E) while casting.
  - **M3E's scheme is seeded the Material You way**: `themeColorOrNull()` (MCU QuantizerCelebi + Score) on a 112px read of the artwork, not the shell's palette colour. That colour is kmpalette's DARK swatch, chosen for Classic's gradient; on a light cover it is often a near-grey whose stray hue `PaletteStyle.Vibrant` blows up into a colour the cover does not have — a pink sleeve came out green.
  - The flat (non-glass) Android bottom bar now folds and unfolds like the glass one: `LiquidGlassAppBottomNavigationBar(liquidGlass = false)` draws `FlatTabBar`/`FlatSearchButton`, and the whole bar grows from the left instead of a circle jumping to the middle. `App.kt` takes that path whenever `getPlatform() == Platform.Android || liquid glass is on`.

- **YouTube comments in Now Playing (2026-10-17, issue #2666)**: a Comments button in every style, never squeezed between the buttons already there (Classic: left cluster, Info · Output · Comments; Apple Music: the last segment of the capsule, Lyrics · [Output | Listen Together | Comments] · Queue; M3 Expressive: the end cap of the connected group, after Queue) opens `CommentsBottomSheet` (`ui/component/`, state in `CommentsViewModel`). It is a `ModalBottomSheet` with `skipPartiallyExpanded = false`: half open first, dragged to full height. Top/Newest, load more as the list nears its end, replies with "Show more replies", and, signed in, post, reply, like and dislike. Signed out, every write opens the sheet's own log-in dialog, whose button goes to `LoginDestination`.
  - **Source: YouTube Music's own Comments tab.** `next(WEB_REMIX, videoId)` answers tabs Up next | Lyrics | Comments | Related. Lyrics and Related carry a `pageType`, Comments does not, and its title is translated ("Bình luận"), so it is found by type: the only tab holding a `sectionListRenderer` that reloads from `reloadContinuationData` (`CommentsPageParser.commentsTabToken`). Turned off, or a live stream with only its chat: the tab holds a `messageRenderer` and is `unselectable`, with no token. `next(WEB_REMIX, continuation)` answers every comments token: first page, next page, sort, replies.
  - **A thread carries only keys.** The comment and its toolbar arrive as `frameworkUpdates` mutations under those keys: `commentEntityPayload` (text, author, `likeCountNotliked`/`likeCountLiked`), `engagementToolbarStateEntityPayload` (`likeState`, `heartState`) and `engagementToolbarSurfaceEntityPayload` (the like/unlike/dislike/undislike `performCommentActionEndpoint` actions and the reply command's `createReplyParams`). Commands are read from raw JSON at any depth, because YouTube rewraps them.
  - **Tokens:** the next page is the top-level `continuationItemRenderer`. A thread's replies token is `commentRepliesRenderer.subThreads[0]` on YouTube Music, `contents[0]` on the WEB client. A replies page lists replies as threads on YouTube Music and as bare `commentViewModel`s on WEB; the parser reads all four.
  - **Writes** (`Ytmusic.kt`): `comment/create_comment` with the header comment box's `createCommentParams`, `comment/create_comment_reply` with `createReplyParams`, `comment/perform_comment_action` with one action token, all through `ytClient(WEB_REMIX, setLogin = true)`. Signed out the toolbar carries a `prepareAccountCommand` instead of commands and the comment box has no submit button; a signed-in account without a channel looks the same, and the sheet says to create one.
  - **Known risk, not handled:** comments posted through InnerTube by low-reputation accounts can be hidden from everyone else (YouTube.js #878) unless the BotGuard attestation the create response asks for (`RunAttestationCommand`, then `att/log`) is run.
  - Comment text goes through `DescriptionView`, which gained an optional `color` (default unchanged): a timestamp seeks the track, only inside its length, and a link opens normally, as in a description. Hashtags, mentions and bold (`commandRuns`, `styleRuns`) stay plain text, as they do in descriptions.
