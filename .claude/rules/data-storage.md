# Data and storage

Notes on the Room database and its SQL traps, DataStore on Windows, and the Coil image cache. Moved from the changelog in `CLAUDE.md`; each entry keeps its original date. Add to this file by the Auto-Update Rule in `CLAUDE.md`.

- **Clear listening history sweeps the whole cached library (2026-08-16)**: one button in Settings → **Listening history** (its own section, above Storage, since Storage is Android-only) wipes `playback_event` and then everything the app kept only because it happened to render it once. Order is the feature: containers first, songs last — sweeping songs alone deleted **0**, because 11 322 of 12 221 were held alive by playlists nothing pruned. The chain is pin-live-queue → `playback_event` → artists (`followed = 0`) → their `notification` + `followed_artist_single_and_album` → podcasts (`isFavorite = 0`, cascades to episodes) → albums → playlists → songs → satellites already orphaned before this ran → `checkpoint` + `VACUUM` → unwind the queue pin. On the owner's 57 MB database: 10 607 songs, 470 artists, 238 playlists, 50 albums, 8 podcasts, 8 818 satellite rows; file down to ~12 MB.
  - **Kept by state, not by reference.** `song.liked` is the *entire* Favorites feature and `song.downloadState` is the *only* link between a downloaded file and its row — neither is a foreign key, so the literal "referenced by nothing" reading deletes both libraries. `downloadState = 0` also spares a download still in flight. Same idea one level up: albums/artists that back a liked or downloaded song are spared so their pages still render offline.
  - **`NOT IN` over a nullable column silently matches nothing.** `local_playlist.youtubePlaylistId` is nullable and mostly NULL; `x NOT IN (…, NULL, …)` is NULL, never TRUE, so the playlist sweep deleted **0 rows and reported no error**. Every such subquery needs `WHERE <col> IS NOT NULL`. This is the same failure shape as the crossfade guard that was dead code on one of two trigger paths.
  - **`_` is a LIKE wildcard and videoIds are full of it.** Ids are matched as quoted tokens inside JSON columns (`'%"' || id || '"%'`), which is sound against the real shapes — including `List<Map<String,String>>` columns, where the id is still a quoted value. But 1 748 videoIds contain `_`, so every pattern escapes `\`, `_`, `%` via nested `replace()` and declares `ESCAPE '\'`.
  - **The DELETE re-checks the orphan conditions** instead of trusting the precomputed id list: the user keeps liking and browsing while the sweep runs, and `pair_song_local_playlist` cascades on song deletion, so a song added to a local playlist mid-sweep would otherwise be pulled straight back out of it.
  - **The live queue is pinned to disk first**, deliberately ignoring `saveRecentSongAndQueue`. The `queue` table is only written on pause / track change / exit and only when that setting is on, so the song playing through the speakers looked orphaned. The pin is removed afterwards when the setting is off.

- **`@RawQuery` cannot VACUUM — Room routes it to a read-only connection (2026-08-16)**: KSP generates `raw()` as `performSuspending(__db, isReadOnly = true, inTransaction = false)`, Room takes a reader connection for that, and readers are opened with `PRAGMA query_only = 1`. `VACUUM` there fails with *"attempt to write a readonly database"* — while `PRAGMA wal_checkpoint` is accepted on the very same connection, which is exactly why the long-standing `DatabaseDao.checkpoint()` works and hid this. `vacuum()` therefore lives on `MusicDatabase` as `useWriterConnection { it.execSQL("VACUUM") }`, with `checkpoint()` immediately before it so the WAL the deletes just filled is folded back in first. `execSQL` opens no transaction, which SQLite requires for VACUUM. A VACUUM failure must not surface as an error: every delete has already committed.

- **Unfollowing an artist now cleans up immediately (2026-08-16)**: `ArtistRepositoryImpl.updateFollowedStatus` only flipped `artist.followed`, stranding that artist's `notification` and `followed_artist_single_and_album` rows forever — and once the artist row itself is swept, those rows lose any way back to an artist. It now deletes them on the unfollow path. The equivalent sweep stays in the clear-history button for rows stranded before this shipped.

- **Windows "Unable to rename settings.preferences_pb.tmp" crash traced to a DataStore race and fixed there (2026-10-04)**: Sentry SIMPMUSIC-DESKTOP-J logged ~26k fatal crashes on Windows from 2025-12 onward, on every release. The race lives inside DataStore 1.2.1. `FileStorageConnection.readScope` only `tryLock`s, and `DataStoreImpl` reads anyway when the lock is busy. A read that arrives mid-save goes to disk, because the cached version is behind between `incrementAndGetVersion()` and the cache update inside that save. That read opens the real file with `FileInputStream`, which the JDK opens without `FILE_SHARE_DELETE` (`io_util_md.c`). On Windows, `Files.move(REPLACE_EXISTING)` begins with `DeleteFile(target)` (`WindowsFileCopy.move`), so the save fails. DataStore swallows the real error and blames "multiple instances". The save had been launched on `SERVICE_SCOPE`, which has no handler, so `CrashDialog` ended the process. `createDataStoreInstance()` on JVM now builds the store as `PreferenceDataStoreFactory.create(storage = ReadsWaitForWritesStorage(FileStorage(PreferencesFileSerializer) {…}))`, which holds one Mutex across `readScope` and `writeScope`. The file and its format are unchanged, so nothing migrates. The race cannot be reproduced off Windows. Confirm the fix by the SIMPMUSIC-DESKTOP-J and -12 rates on the next release: an outside program holding the file would still fail a save, and 1.2.1 hides which one did.
  - **Bumping DataStore does not fix it.** `650ccfb4d` (in 1.3.0-alpha03 and later) only adds `ATOMIC_MOVE` and stops swallowing the error. The unlocked `FileInputStream` read is still on androidx-main, and b/203087070 carries a report of the crash on 1.3.0-alpha10. What `ATOMIC_MOVE` would buy is diagnosis and safety: it attaches the real Win32 error, and it removes 1.2.1's window in which the delete succeeds, the move fails and the settings file is lost.
  - **The same race also crashes the reader.** SIMPMUSIC-DESKTOP-12 logged ~300 crashes on 18 machines from 2025-12 onward, still on 2.2.0. A read that opens the file between the save's `DeleteFile` and `MoveFileEx` gets `FileNotFoundException` ("cannot find the file specified"). `FileReadScope.readData` then checks `file.exists()`. If that returns false, still inside the gap, the read silently returns empty preferences. If it returns true and the retry fails, DataStore throws "Inoperable file". The lock closes both.
  - **Do not switch the read to NIO**, even though NIO shares delete. On Windows without POSIX delete semantics, the delete goes pending and the move fails, and DataStore then deletes the `.tmp`. The settings file is gone.
  - **The trigger was ours.** `skipSegmentsJob` asked `sponsorBlockEnabled.first()` on every progress tick, against the 5 s position save. That was 20 reads a second once 2.2.0 smoothed the published position (3–4 before), and ten times that with SponsorBlock on, because `getSponsorBlockCategories()` reads each of the nine categories. The check now reads `sponsorBlockCategories`, a `MutableStateFlow` that a collector in `init` keeps current from those settings (null while SponsorBlock is off or not loaded yet), so no tick touches DataStore. Android's `MediaServiceHandlerImpl` had the identical per-tick read and got the identical change. The two handlers' SponsorBlock blocks must stay identical.
  - **The lock is safe only because of how DataStore enters it.** It enters the connection through `readData()` and `writeScope`, and neither runs inside the other. It also always takes its own coordinator lock before the wrapper's. Re-check both on any DataStore bump. The Desktop backup and restore (`backupNative`, `restoreNative`) still read and write the file directly, outside the lock.

- **Coil images use a 24-hour TTL, then network with forced stale-cache fallback (2026-10-06)**: the main Android and Desktop singleton loaders register `utils/NetworkFirstInterceptor` from `composeApp/commonMain`. HTTP(S) requests first read RAM/disk with network disabled: an image younger than **24 hours (86,400,000 ms)** is returned without an Internet request. At exactly 24 hours, or on a cache miss, the loader attempts a network refresh. Success updates the image and its age; failure returns the previously decoded cached image **regardless of TTL**. Expiry never deletes an entry, and neither a cache hit nor a failed refresh renews its TTL. Local files/resources and explicitly cache-only requests keep Coil's original behaviour. Expired-cache refresh is not stale-while-revalidate: it must fail or time out before the stale image is displayed.
  - **Age survives a restart.** Disk entries already contain `NetworkResponse.responseMillis`; the interceptor reads it through `CacheNetworkResponse.readFrom` and carries that same timestamp in the RAM value's `simpmusic#image_response_millis` extra. Warming RAM from disk must not replace that timestamp with the current time. Unknown/invalid timestamps are stale but remain usable for fallback. `CacheNetworkResponse` is an internal Coil API: re-check its metadata reader on a Coil bump. The injected clock and `ttlMillis = 0` keep tests deterministic without sleeps.
  - **Failed responses must not overwrite the fallback.** Coil 3.6.3 writes responses before decoding and its default strategy caches some failure codes, including 404. The interceptor downloads under a unique temporary key in the SAME `image_cache`, then copies the encoded bytes and metadata through `DiskCache.Editor` to the original key only after decoding succeeds. It repairs the RAM entry's source key and removes the temporary entry in `finally`, including cancellation. Requests for the same disk key are serialized, with the lock removed after the last user. A cache-write failure does not hide a successfully downloaded image.
  - The directory (`SYSTEM_TEMPORARY_DIRECTORY/image_cache`), 512 MiB limit, original cache keys and image quality are unchanged. There is no new cover store, database field, dependency or download format. Widget/notification/download thumbnail code that constructs a separate `ImageLoader(context)` is deliberately unchanged. Existing entries remain available for offline fallback; this does not pin them against ordinary LRU eviction or manual cache clearing. A process killed mid-request can leave a staging entry until normal cache eviction.
  - `composeApp/src/jvmTest/.../NetworkFirstInterceptorTest.kt` has 14 cases against real Coil memory/disk caches and its network fetcher with an in-process fake client/decoder: fresh RAM/disk hits skip the network, disk-to-RAM warming preserves age, exact 24-hour expiry refreshes and starts a new TTL, failed refresh forces expired cache without renewing TTL, plus HTTP/decode errors, cache miss, custom keys, local files, cache-only requests and cancellation. Tests were added but not run by the agent (no-auto-build rule); generic kotlin-lsp diagnostics are not a KMP compile gate.
