# Playback engine: crossfade, queue, radio and live streams

Notes on both platforms' player handlers and adapters: crossfade rules, the sleep fade, queue and radio behaviour, live streams and published playback state. Moved from the changelog in `CLAUDE.md`; each entry keeps its original date. Add to this file by the Auto-Update Rule in `CLAUDE.md`.

- **Crossfade skips video tracks (2026-08-01)**: both `CrossfadeExoPlayerAdapter` (Android) and `MpvPlayerAdapter` (Desktop) skip the crossfade path when the NEXT track will play as video (`isVideo()` + watch-video setting on — the same condition that builds a merged audio+video source). The merged two-URL source is error-prone to prepare mid-fade and used to cut the outgoing song short or jump straight to the video at 0:00; such transitions now take the normal (non-crossfade) path. **Update 2026-08-05**: the CURRENT-track check — removed on Android in commit `9da155d7` because its old shape ignored the watch-video setting — is back on both platforms as `isCurrentTrackVideo()` (`watchVideoEnabled && isVideo()`, symmetric with `isNextTrackVideo()`), so a video also plays out to its last frame instead of fading out under the incoming song.

- **Sleep timer fade-out, and a second volume line to carry it (2026-08-14, issue #2330)**: the sleep timer used to end on a bare `player.pause()`. It now ramps to silence over 5 s on an equal-power (cosine) curve, then holds silence for `sleepFadeTailMs = 800` before stopping. The attenuation rides a **line of its own**, deliberately not `volume`: that one is the user's level and is reported back through `onVolumeChanged`, so ramping it would drag the UI slider down and — if the process died mid-fade — leave a silent app behind. `MediaPlayerInterface` gained `var sleepFadeFactor: Float` for it.
  - **Android** applies it as a new `SleepFadeAudioProcessor` in the Media3 chain (`arrayOf(crossfadeFilter, sleepFade)`), one instance per ExoPlayer, all reading the same `@Volatile` field. **Desktop** adds a third mpv level: `MpvPlayer` now blends `masterPercent × sleepPercent` into `ao-volume` while `fadePercent` keeps carrying the crossfade on the software `volume`. Crossfade and sleep fade therefore never share a variable and simply multiply.
  - **Tail exists because gain sits ahead of the sink.** AudioTrack buffers 250–750 ms, so pausing the instant the ramp hits zero still cuts at roughly −12 dBFS. Fade + tail are clamped to fit inside `remaining`, or the timer overruns the track and pauses inside the next one.
  - **The restore must not be queued by the caller.** `pause()` is asynchronous on both platforms *and* suspends partway through (`commitIncomingAsCurrent` joins a job), so a single-thread dispatcher does **not** order "pause then restore" — the suspension releases the thread and the restore runs first, re-opening the mixer over the last of the audio. Each adapter therefore restores the factor itself, in a `finally` at the end of its own pause task; the handler only restores on the cancelled path. The Android cast branch returns before that coroutine, so it clears the factor inline — skipping it leaves every sample multiplied by ~0 for the rest of the process.

- **Crossfade exclusions: short tracks and albums (2026-08-14)**: crossfade is now skipped when the current track is shorter than `max(20 s, crossfadeDuration × 3)` — at the default 5 s fade a 20 s track spent half its length fading. With duration on Auto the bar is computed from `resolveAutoCrossfadeDurationMs()` (20–45 s), never a hardcoded default. Separately, an opt-in setting (**off** by default) skips crossfade *between tracks of the same album*, so an album sequenced to run continuously still does.
  - Albums are recognised by a new `PlaylistType.ALBUM` (behaves exactly like `PLAYLIST` elsewhere; `AlbumViewModel` uses it for play, but **not** for shuffle — once shuffled the running order is gone). The handler snapshots the album's `mediaId`s into `MediaPlayerInterface.albumTrackIds` at load time, and crossfade is skipped only when **both** the current and the next track are in that set — which is exactly what keeps the edges intact: the last album track into the first radio track still fades. A **set of ids, not a count**, because shuffle reorders the queue including appended radio.
  - This works only because endless queue appends through paths that write `_queueData` directly and **never call `setQueueData`**, so the snapshot stays album-only while `listTracks` grows. Routing those appends through `setQueueData` would swallow the radio tracks into the set and disable crossfade for the whole queue.
  - Known limitation: the tag does not survive a restart — the queue-restore path hardcodes `PlaylistType.PLAYLIST` because `QueueEntity` has no column for it.

- **Every crossfade guard belongs on BOTH trigger paths (2026-08-14)**: crossfade starts from the **position-polling job** (`timeRemaining in 1..crossfadeDuration + prep`, polled every 200 ms), and *separately* from `handleTrackEndInternal()` on EOF. The EOF path returns early when `isCrossfading` is already set, so a condition added only there is **dead code with no symptom** — the feature silently does nothing. The existing video checks were on both paths; that is the pattern to follow.

- **Seeking mid-crossfade (2026-08-14)**: `seekTo(positionMs)` was the only transport command that did not handle `isCrossfading` — on both platforms. Two bugs at once: the outgoing track kept playing because nothing cancelled the crossfade, and the seek landed on the *wrong* track, since position updates during a crossfade are read from `secondaryPlayer` while the seek went to `currentPlayer`. Both now commit the incoming track as current first, the way `pause()` does.

- **Playback state was published inverted on both platforms (2026-08-16)**: `onIsLoadingChanged` wrote 2–3 times in a row — `Loading` unconditionally, maybe `Ready`, then `Loading` again from `stopBufferedUpdate`. `_simpleMediaState` is a `StateFlow` collected from another thread, so it conflates and the UI settled on the **last** write: `Loading` when buffering had just *finished*, `Ready` when it had just *started*. Since the adapters call it with `false` immediately after announcing `STATE_READY`, every track start and every resume ended with a spinner over playing audio. Compounded by `startBufferedUpdate()` not cancelling its predecessor, so each track leaked another 500 ms `Loading` emitter — the sibling `startProgressUpdate()` had already been fixed for exactly this (#2152). Desktop additionally compared `bufferedPercentage * duration` (percent × ms) against `currentPosition` (ms), off by ~100×. All of it predates the mpv migration (blames to the VLC-era handler), and Android was affected identically.
  - Two more, in the same family: `SharedViewModel`'s `Ended` branch pinned `current = -1L`, and the only formatter renders any negative as `NA:NA` — with the `Progress` branch ignoring negatives and the `Loading` branch restoring `total` without touching `current`, the player showed a correct duration next to `NA:NA`. And `play()` at end of queue called into a handle parked at EOF, which does nothing, so the button looked ignored; both adapters now rewind first.

- **Wrapped queue rows were being dropped — 82% of a logged-in radio (2026-08-16)**: `YouTube.next()` read `it.playlistPanelVideoRenderer` only, so every row YouTube ships as a `playlistPanelVideoWrapperRenderer` resolved to null and vanished in the `mapNotNull` that builds the queue. Measured on a live logged-in radio: **161 of 197 rows across four pages were wrapped**, so a 50-track first page arrived as 6. Reading `Content.track` (bare renderer, else `primaryRenderer`) fixes it.
  - **The wrapper only appears when authenticated.** Six anonymous requests eliminated the other variables one at a time — same seed, both client versions (`1.20260304` and `1.20260811`), and both body shapes (plain `NextBody` and the `isAudioOnly` + `params=wAEB` one) — every one returned zero wrappers, while the authenticated capture returned 48/50. All three radio paths use `youTube.next()` with `setLogin = true`, so the app has been getting the wrapped shape.
  - `Content.counterpart` is now parsed too: it holds the *other* rendition of the same recording, which is what powers the official client's Song/Video switch.
  - `nextCustom` (`setLogin = false`, hardcoded `RDAMVM$videoId`) is dead code — nothing calls it.

- **Radio queues can be kept audio-only (2026-08-16, issue #2334)**: an opt-in setting (**off** by default) that drops video entries from radio queues only — deliberately not a global "hide all video" switch, so a playlist or album the user picked still plays what it contains. Filtering lives in `SongRepositoryImpl` because that is where the three queue sources meet: `getRadioFromEndpoint`, `getRelatedData` and `getContinueTrack`.
  - **Substitution is impossible, so entries are dropped.** Every video that actually reached the measured radio was `MUSIC_VIDEO_TYPE_UGC` — a fan remix or mashup that exists only as a video and ships **no `counterpart`** to swap in. Official music videos never arrive as the primary rendition at all: YouTube already demotes those to the counterpart of the audio track. Rate is roughly 1 entry per 50, so the queue barely shortens.
    - *Superseded 2026-09-25* — that measurement was a radio started from a **song**. A radio started from a **video** is nothing but videos (a UGC seed: 38 OMV, 11 UGC, 1 podcast episode, no song), so dropping every video emptied the queue outright. The setting is now **"Play audio version instead of MV in radio"**, the same idea as YouTube Music's own *Don't play music videos*: a video row whose song rendition YouTube shipped alongside it (`SongItem.counterpart`, from `NextPage.fromPlaylistPanelContent`, logged-in responses only) is swapped for that song; a video with no song version is skipped as before; and a page left empty is kept as it came, since a radio that plays videos beats one that plays nothing. `preferAudioWhenRadioAudioOnly` logs rows / swapped / kept per page — whether a logged-in video radio really carries song counterparts was not measured, only inferred from the song-radio wrappers.
  - Each source needs its own radio test, and two of them are not obvious. `getContinueTrack` must also accept **`RRDAMVM…`** — YouTube's other spelling for a single video's radio, which `isRadioQueueId` deliberately does not match because it never appears as a queue's own `playlistId`; and its `else` branch continues a real playlist, so only the `!fromPlaylist` branch may filter. `getRelatedData` is **always** radio but not directly: `next(videoId)` alone answers with just two rows — the song and an `automixPreviewVideoRenderer` pointing at its `RDAMVM…` radio — which `YouTube.next` then follows and splices in.
  - `getRadioFromEndpoint` is shared with the **shuffle** button on playlist and artist pages, which passes the playlist's own id — `isRadioQueueId()` returns false there, so shuffle is untouched.

- **Radio queues trim their own history, and the per-append queue scan got cheap (2026-09-21, issue #2504)**: a radio queue keeps 100 played tracks behind the current one and drops the oldest once the history passes 120 (`RadioQueueTrim` in `core/domain`), so a listener can scroll back at most ~147 played tracks. Nothing ahead of the playing track is ever touched, and a playlist or album is trimmed only after *Endless queue* has carried it past the list the user picked — at which point `loadMore` re-points it at the last track's radio and now also re-types it `PlaylistType.RADIO` (in BOTH of its Endless branches), because from there on it IS a radio.
  - **`PlaylistType.RADIO` does not mean "a radio".** Favorites, Downloaded, Most played, Monthly recap, Your top tracks and the Analytics lists are queued as `RADIO` with `playlistId = null`, and a playlist's Shuffle is queued as `RADIO` with the playlist's own id. The first version gated on the type alone and trimmed all of them. `RadioQueueTrim.appliesTo` now requires the type AND a YouTube radio id: `RD…`, minus `RDCLAK…` (a curated playlist, which has an end).
  - **`reorderShuffledQueue` was the stall in #2504, not the appends themselves.** `loadMoreCatalog` adds a batch one track at a time, so it fires ~50 timeline events; each one re-matched the whole queue with a nested search (queue × player string compares) and built three log lines containing every title, then threw the result away when the sizes disagreed. It is now a map lookup and logs sizes only. The first shape of this fix — an early return when the player list is shorter — was **wrong**: `loadMoreCatalog` updates `queueData` once at the END, so mid-batch the PLAYER is the longer list.
  - **`MediaPlayerInterface.removeMediaItems(from, to, onRemoved)`** removes a range of played tracks in one pass (one precache top-up, one timeline notification). Removing one at a time would repeat exactly the storm above. The default refuses; only the two real adapters remove anything.
    - Both adapters re-check everything INSIDE their own launch (issue #2156's crash shape).
    - They refuse while `isCrossfading`: `crossfadeFromIndex` indexes the same playlist and is not shifted, so a cancelled fade would revert to a track ~100 positions away.
    - They refuse while shuffle is on: the tracks before the current one in the unshuffled list are then still to come.
    - Android also refuses while casting: `CastHandoffManager.remoteToPlaylist` holds absolute playlist positions, so shifting them sends the receiver the wrong tracks.
    - They do NOT call `clearPrecacheExceptCurrentInternal()`. That releases every precached handle, including the one the next crossfade is about to use; the removed tracks are all behind the playhead and precache is keyed by `mediaId`.
  - **`queueData` is cut by the removal's own answer, never by a guess.** The adapter calls `onRemoved(removedIds)` exactly once, on its own thread, from INSIDE the removal and before anything else can run. It passes an empty list when it refuses. The handler cuts `listTracks` right there, only if those ids are exactly its front (`RadioQueueTrim.afterFrontRemoved`). An `AtomicBoolean` in-flight flag stops a second request until the answer arrives.
    - The first version recorded an expected size and inferred the outcome from later timeline events, and **that broke Desktop outright**. `MpvPlayerAdapter.notifyListeners` QUEUES listener calls, each carrying a snapshot, so a batch's own add events arrived after the request and cleared it before the removal ran. The player was trimmed and `queueData` was not, for good.
    - With `queueData` longer than the player, the load-more check (`listTracks.size - player.currentMediaItemIndex < 3`) never fires again, so **the radio stopped** about 50 tracks later.
    - Two requests in flight at once (a batch plus a crossfade end, or a batch plus Add to queue) cut twice for the same reason.
    - Offset lists are the "tap a queue row, play the wrong song" bug, and `reorderShuffledQueue` bails on a size mismatch, so nothing heals them.
  - **Shuffle is excluded on purpose.** `currentMediaItemIndex` and the indices `removeMediaItems` takes count the UNSHUFFLED playlist, while `getCurrentMediaTimeLine()` and `listTracks` are in shuffled order, so the oldest-played tracks are not a contiguous range there at all. Radio with shuffle on keeps its full history.
  - `TRIM_ABOVE_HISTORY` is 120, not the ~150 the history is meant to stay under: the check runs right after a batch append, and a radio appends roughly every 50th track, so a threshold is only crossed at ~47, ~97, ~147, ~197… At 150 the first cut waited until ~197; at 120 it lands at ~147 and the history swings 100…~147.
  - **With crossfade on, the batch lands mid-fade and the trim is refused** — the batch is requested by the transition that STARTS the fade and arrives 1–3 s later, inside a 5 s default fade. Without a retry, crossfade users would never be trimmed; the handlers therefore call `trimRadioHistoryIfNeeded()` again from `onCrossfadeStateChanged(false)`. That retry is **posted, never run inline**. Android calls `onCrossfadeStateChanged` from inside its own code: Next mid-fade commits the incoming track, then posts a seek to an index it has just computed. An inline trim therefore queued the removal ahead of that seek, and the seek landed ~47 tracks later. The fade remembers the track it may revert to as a playlist POSITION (`crossfadeFromIndex`), and an id would not do instead: a radio repeats songs, so ids are not unique in a queue.
  - **Anything that holds a queue POSITION over time must expect the queue to shrink from the front.** Before this, only the user's own actions shortened it.
    - `playNext` records just its insertion and applies it to the current list inside `_queueData.update`. It used to write back a copy of the whole queue taken before `getSongInfo` suspended, which silently undid a trim that landed meanwhile.
    - The handlers' `removeMediaItem`/`moveItemUp`/`moveItemDown` check the position against the current queue and edit it inside `update`.
    - The queue ⋯ sheet, on both queue screens, remembers which track it was opened for and does nothing once that track is no longer at its position.
    - Android's `removeMediaItem`/`moveMediaItem`/`replaceMediaItem` and Desktop's `replaceMediaItem` re-check bounds inside their launch (#2156's crash shape).
    - `reorderShuffledQueue` writes only over the exact list it read (`it.data.listTracks === listTrack`). On Desktop, Add to queue runs it on the UI thread right after requesting a trim, while the cut lands on the player thread; writing its snapshot afterwards put the trimmed tracks back.
  - Queue rows (the Classic/M3E sheet and the Apple Music queue) are keyed `videoId#occurrence` instead of `index + videoId`: a front trim changes every position, so a position-based key made the whole list lose its scroll anchor and jump under the user.
  - Now Playing's artwork pager snaps instead of animating when the index moves more than one page — a trim drops it by ~47 without changing the track, and animating that flings the pager through dozens of covers.

- **Live broadcasts play (2026-10-01)**: YouTube Music's "Station" shelf (e.g. Walker Stations, `9l63T77YL2c`) is 24/7 live streams, and every layer of playback assumed a fixed length. A live video is recognised by `PlayerResponse.VideoDetails.isLive` — NOT `isLiveContent`, which stays true on the recording a finished broadcast leaves behind — and plays from its HLS playlist.
  - **Nothing says a queue item is live until its stream resolves.** Queue rows (`next`) carry no LIVE chip — a live seed shows only its elapsed time as `lengthText` — so `StreamRepositoryImpl.getStream` records every resolution in `LiveStreamRegistry` (`core/domain`; in memory on purpose — a broadcast ends, and the next run re-learns it). *(Corrected 2026-10-16: this used to say search results do not mark it either. They do, and so do playlist rows; see "Live items are marked from the parser down".)* Both adapters and `SharedViewModel` (`TimeLine.isLive`) read it from there. Live streams are deliberately NOT written to the format table.
  - **Extraction — only the YouTube Android client's HLS keeps playing** (measured 2026-10-01 on `9l63T77YL2c` / `QJXse_NH9Ho`, signed in and anonymous): WEB_REMIX, WEB, `web_safari` and MWEB return playlists that load (200) but every segment is refused (403 — GVS PoToken); IOS 21.26.4 and TVHTML5 send no HLS for a live stream; `ANDROID_VR` 1.65.10 plays and then refuses every segment from ~30 s in while its playlist keeps refreshing (mpv: `paused-for-cache`, then idle — the user saw an endless spinner), although yt-dlp's policy still marks its HLS as not needing a PoToken. `ANDROID` 21.26.364 (`YouTubeClient.ANDROID`, versions from yt-dlp's INNERTUBE_CLIENTS) played 130 s straight with segments 200 throughout. `Ytmusic.liveStreamPlayer` sends no cookie and a fresh anonymous `visitorData` from `visitorData()` (sw.js_data): with none every client is bot-checked, and ANDROID_VR also refused the session's own stored one. `YouTube.player()` checks `isLive` BEFORE the OK-status gate — `videoDetails` is present even on a refused response — and takes `liveStreamHlsUrl()` first, then `Extractor.liveHlsUrl()` (PipePipe/BravePipe tiers returning `StreamInfo.hlsUrl`, kept apart from `newPipePlayer` because every tier there rejects a result without regular audio+video itags) as a fallback. `tempRes`'s own `hlsManifestUrl` is deliberately NOT a fallback: it is the web kind. The response goes out through `asLiveStream(url)`: HLS only, formats emptied. **Re-measure with a 2-minute run before trusting a client**: the 30-second cut-off is invisible in a short test.
  - **Android cannot know a track is live before building its source.** `DefaultMediaSourceFactory` picks progressive vs HLS when the MediaItem is set; the URL is only resolved later, in `ResolvingDataSource`. So the progressive resolver throws `LiveStreamDetectedException` once the registry knows, `CrossfadeExoPlayerAdapter.onPlayerError` loads the track again, and `MergingMediaSourceFactory` then builds an `HlsMediaSource` on `simpmusic-live://playlist/<id>`, resolved through a plain-HTTP `ResolvingDataSource` (no cache, no 5 MiB chunks — segment URLs are real). `LiveStreamAwareLoadErrorHandlingPolicy` stops the Loader backing off for seconds on an error a retry can never fix, and a precached player that already errored is dropped instead of promoted. All of it lives in `media3/.../mediasourcefactory/LiveStreamPlayback.kt`.
  - **Desktop**: mpv plays HLS itself, so `extractPlayableUrl` hands it the playlist without the `edl://` merge (the playlist carries audio and video). The Linux FFmpeg build disables no demuxers and enables the `hls` protocol.
  - **`reconnect_streamed=1` breaks live HLS in mpv.** The app's `stream-lavf-o` (`reconnect=1,reconnect_streamed=1,reconnect_delay_max=30`, the VLC-era http-reconnect) made a live playlist play 3–4 s and then stall — or report EOF, which `handleTrackEndInternal` turns into "next track": the build that first played a live stream skipped it after ~2 s. Measured on libmpv 0.37, audio-only and video alike: 4 s played in 20 s with the option, 17 s without; `reconnect=1,reconnect_delay_max=30` alone is fine. `MpvPlayer.create(liveStream = true)` drops only `reconnect_streamed`, chosen through `PlayableSource.isLive`.
  - `SharedViewModel`'s Progress branch treats `total <= 0` as still loading, which a live stream on Android (ExoPlayer duration `C.TIME_UNSET`) would be forever — `TimeLine.isLive` exempts it.
  - Live tracks skip crossfade on BOTH trigger paths (near the live edge mpv's "time remaining" looks like a song's last seconds), skip precache and `seekTo`, and Previous goes to the previous track instead of restarting. Seek bars read `TimeLine.lengthLabel()` / `elapsedLabel()` (`AllExt.kt`) and show `LIVE`. No lyrics provider is asked for a live track: `SharedViewModel.getLyricsFromFormat` returns early for it, and every lyrics fetch comes through there (on Desktop the seek-window "duration" would otherwise trigger one).
  - **LIVE badge**: Home's "Station" shelf is served signed-in only; its cards are `musicTwoRowItemRenderer` with `subtitleBadges: [{liveBadgeRenderer: {label: "Live"}}]` (read off a signed-in response). `Badges.liveBadgeRenderer` → `MusicTwoRowItemRenderer.isLive` → `Content.isLive` → a red chip ahead of the channel name in `HomeItemVideo`. The badge only decorates the card; playback still learns liveness from stream resolution.

- **Queue rows open the full song sheet, and queue edits respect shuffle (2026-10-04)**: a row's ⋯ in every queue — the Classic/M3E sheet (`QueueBottomSheet`, opened from Now Playing, the fullscreen lyrics page and the Desktop capsule) and the Apple Music queue tab — now opens `NowPlayingBottomSheet` for that track with `queuePosition` set, which adds Move up, Move down, Move to play next and Delete from queue above the usual rows and drops Play next and Add to queue — the track is already in the queue. `QueueItemBottomSheet` (those three rows alone) is gone. `QueueBottomSheet` hosts the sheet itself and so takes a `navController` plus `onNavigateToOtherScreen` (`MiniPlayer` gained an optional `navController`, passed by `App.kt`); the Apple Music queue goes through `NowPlayingContentActions.onQueueItemMore` to the player screen. The queue rows act only if their track is still at the position the sheet was opened for, as before.
  - **Queue positions are SHUFFLED positions while shuffle is on, and three operations ignored that.** `reorderShuffledQueue` keeps `listTracks` in the shuffled play order, and tapping a row already translated it (`getUnshuffledIndex` in `playMediaItemInMediaSource`), but move up/down and delete handed the shown position straight to the player as a playlist index — touching a different track than the one picked. Removal now translates the position the same way; moves go to the new `MediaPlayerInterface.moveShuffledItem(from, to)`, which reorders only the adapter's own `shuffleOrder` (default no-op; implemented in `CrossfadeExoPlayerAdapter` and `MpvPlayerAdapter`). Turning shuffle off still restores the original order. The Android `swap` (drag to reorder) takes the same branch; Desktop's `swap` already loops over move up/down.
  - **Both adapters used to reshuffle the WHOLE order on every edit while shuffle was on** — `moveMediaItem` and `removeMediaItem` both ended in `createShuffleOrder()`. Removal now drops just that track from `shuffleOrder` (`removeFromShuffleOrder`) BEFORE anything reads the order (precache, next track), and removing the playing track hands over to the next one in the shuffled order rather than the next playlist entry. `moveMediaItem` still reshuffles, but the handlers no longer call it while shuffle is on; `replaceMediaItem` also still does.
  - `MediaPlayerHandler.moveItemToPlayNext(position)` targets the slot right after `currentOrderIndex()`: `current + 1` from ahead, `current` from behind (the track leaving its slot shifts everything after it). Up/down/play-next share one `moveQueueItem`, which updates queueData only if the track is still at `from` — the player's own timeline event rebuilds the queue in the moved order too, and on Desktop it can arrive first, from the player thread.

- **Add to queue is disabled where the queue has no end (2026-10-10, FR #1469 group)**: Add to queue appends to the END of the queue, and Play next goes right after the current song. Two kinds of queue never reach an end: a radio or mix, and any queue while Endless queue is on. In those, Add to queue stays visible but disabled, with the reason in brackets, the same way Playback speed & pitch is disabled during crossfade. Play next is never blocked.
  - **One rule, in `core/domain`**: `QueueData?.addToQueueBlock(endlessQueue)` (`MediaPlayerHandler.kt`) returns `RADIO`, `ENDLESS_QUEUE` or null. `RADIO` wins, since turning Endless queue off would not lift that block. Radios and mixes are recognised by the id alone, through `String.isEndlessQueueId()` (`RD…` minus curated `RDCLAK…`, `VL` stripped), which `RadioQueueTrim.appliesTo` now shares. The type is not checked because a mix opened from its playlist page is queued as `PLAYLIST`.
  - **Every Add to queue button** reads it through `rememberAddToQueueBlock()` and `addToQueueLabel()` in `ModalBottomSheet.kt`: the song menu, the multi-select sheet, the playlist/album sheet and the local playlist sheet. A new Add to queue entry point must use the same pair.
  - **The swipe on a song row** goes through `SharedViewModel.addListToQueue`, which plays a single song next whenever Add to queue is blocked (it used to do so only under Endless queue). Its icon switches to Play next while that applies.
  - The owner decided against a Spotify-style Add to queue that plays before the rest of the queue, against a two-way swipe, and against a setting for the default action. Report those requests as decided, not as missing work.

- **Live items are marked from the parser down, and downloads refuse them (2026-10-16)**: downloading a live broadcast used to "succeed" on Android with the HLS playlist text saved as the song (`getStream(isDownloading = true)` returned the playlist URL), and failed on Desktop only by accident ("Audio format url is null"). Measured on live WEB_REMIX responses: YouTube puts the LIVE chip (`liveBadgeRenderer`) on search rows and playlist rows (`musicResponsiveListItemRenderer.badges`), on Home's live shelf (`musicTwoRowItemRenderer.subtitleBadges`) and on search's top card — and **not** on queue rows (`next`). Live rows carry `MUSIC_VIDEO_TYPE_UGC` like any upload, so `musicVideoType` cannot tell them apart.
  - **Parser:** `isLive` on `MusicResponsiveListItemRenderer`, `MusicTwoRowItemRenderer` and `PlaylistPanelVideoRenderer`, copied into `SongItem.isLive`/`VideoItem.isLive` at all 17 places those are built. Search's top card is not parsed: the app never calls `SearchSummaryPage`.
  - **Models:** `Content.isLive` is a field; `Track` and `SongEntity` carry it as `resultType == LIVE_RESULT_TYPE` ("LIVE"), read through the extension properties `Track.isLive`/`SongEntity.isLive` in `ModelToEntity.kt`. **No migration**: `resultType` was dead for songs (labels nothing reads, no query filters on it). **Not `videoType`**: both handlers rewrite it from YouTube's value on every play, so a marker there lasts one play. `SongsResult`/`VideosResult`/`ResultVideo` use the same marker; `ResultSong` has no `resultType`, so it got a plain `isLive`. Keep the extension properties off the entity class, where Room would have to decide whether a getter is a column.
  - **The stored row:** `insertSong` is IGNORE, so `LocalDataSource.insertSong` raises the marker itself (`markSongLive`): on an existing row when the incoming one is live, and on any row whose stream `LiveStreamRegistry` already knows is live — resolution (a precache, say) can run before the row exists, and an UPDATE on a missing row is lost. It raises only, because a source without the chip has not said the broadcast ended. Stream resolution is the one writer that also clears it (`updateSongLiveStatus`), so a finished broadcast downloads normally again. `LiveStreamRegistry` still decides playback routing; the row is for the UI and the download gate.
  - **UI:** the shared `LiveBadge` (ex-private in `AdapterItems.kt`) sits ahead of the artist in `SongFullWidthItems` (all 16 song-row call sites, both queue views included), `QuickPicksItem` and `SuggestItems`. `SongFullWidthItems` ORs the list model with the stored row it already observes, which is how a queue row gets the badge once the stream has resolved.
  - **Download gate, three layers:** the ⋯ sheet's Download row is disabled with its reason in brackets (`download_disabled_live`); both `downloadTrack` implementations refuse a row marked live and reset its state (every download path ends there); and resolution refuses what nothing had marked yet — `getStream(isDownloading = true)` emits no URL for a live stream, `YouTube.download` fails with "Live streams cannot be downloaded".
  - Legacy left as is: rows stored before this stay unmarked until a chip or a stream resolution marks them, and a playlist file already saved by an older build is not cleaned up.
