# UI design: headers, glass, theme and layout direction

Notes on shared UI design: the immersive headers, liquid glass, haze, the settings layout, the dark theme, right-to-left layout, the Desktop title bar, the Desktop sidebar, the Desktop frame governor and the icon migration. Moved from the changelog in `CLAUDE.md`; each entry keeps its original date. Add to this file by the Auto-Update Rule in `CLAUDE.md`.

- **Icons unified on Material Symbols (2026-08-03)**: `material-icons-core`/`material-icons-extended` are gone, and so are the XML icon drawables — every icon is now a generated `ImageVector` under `ui/icon/`, addressed as `SimpIcons.<Name>`. Two migrations fed into this: 59 icons replacing `Icons.*` (117 call sites), then 25 more replacing `painterResource(Res.drawable.baseline_*)` (167 call sites, 44 XML files deleted). `RippleIconButton`, `LiquidGlassIconButton` and `ActionButton` changed from taking `DrawableResource`/`Painter` to `ImageVector`. See **Common Tasks → Add a New Icon** for how to add one and which traps to avoid. Icons whose colour carries meaning (`baseline_downloaded`, `baseline_favorite_24`), the logos (`mono`, `monochrome`) and the `holder*` bitmaps deliberately stay as resources.

- **Apple Music header reaches Desktop (2026-08-17)**: the immersive header on Album, Playlist, LocalPlaylist and Artist was gated behind `isMobilePortrait = getPlatform() == Platform.Android && wDP < hDP`, so Desktop only ever saw the old black-and-gradient layout. The gate is now open on all four, and the three list screens carry an **Apple Music desktop header**: square 280dp artwork on the left, and a right-hand column holding title → subtitle in the app accent (`seed`, standing in for Apple's brand red) → meta → the existing `[Shuffle][Play pill][Download]` cluster, re-aligned from centred to left. Everything below the header — `DescriptionView`, the track-count line, the list — is untouched, and the portrait header is unchanged on phones.
  - **The buttons that floated on the artwork have to move.** Back, like, search, `⋯` and LocalPlaylist's AI-suggest were overlays on an edge-to-edge image; at 280dp there is nothing to overlay, so they become a plain top row. Their code is moved verbatim rather than rewritten — each is wired to its own view model.
  - **`aspectRatio(1f)` is a phone-only assumption.** Artist's header used it, which on a 1400dp-wide window makes a 1400dp-tall block: the artwork — or a playing Spotify canvas — swallows the whole page. It is now `height((screenInfo.hDP / 2).dp)`, matching the other three. Two things must change with it or the result is worse than before: `ContentScale.FillWidth` → `Crop` (FillWidth scales a square source to the frame's *width* and shows only its top slice), and the colour scrim measured as `wDP * 0.7f` → `hDP * 0.35f` (70% of the frame's own height; on a wide window 70% of the width is taller than the artwork and covers everything).
  - **`HazeProgressive` kills the process on skiko.** haze 1.7.2's progressive path calls `ShaderBrush.createShader(Size)`, whose mangled signature does not match the Compose this build pins (`material3-multiplatform 1.12.0-alpha01` / skiko 0.148.1) — `NoSuchMethodError` thrown inside the draw pass, `RenderEffect.skiko.kt:234`. Its only user was ArtistScreen's bottom fade, latent because Desktop never rendered that branch. *(Updated 2026-09-23: removed there on both platforms, so nothing uses it now. On Android it also drew a visible seam across the artwork at the top of its 200dp box, even with `startIntensity = 0f`. The fade is now a `Modifier.blur` copy of the artwork masked by a `DstIn` gradient, which is fully transparent where the ramp starts and so cannot leave a seam; below Android 12 blur is a no-op and only the colour scrim remains.)* Plain `hazeEffect` is fine on Desktop. Fixing it properly means moving haze or Compose, and Compose is pinned for a reason — alpha02 bumps skiko to 0.148.2, which removes `Matrix33.makeTranslate` and crashes compottie.
  - **mpv decides the video's fit, not Compose.** `MpvVideoFrames` reports its box size through `setTargetSize`, and mpv scales *and letterboxes* each frame into exactly that size — the black bars are already pixels by the time Compose sees them, so no `ContentScale` can remove them. `MediaPlayerView.jvm.kt` had therefore been ignoring `cropToBounds` outright, with a comment that Desktop never renders the portrait canvas. Cropping is now mpv's `panscan` property (`0.0` letterbox … `1.0` cover), exposed as `MpvPlayer.setPanscan()` and applied from a `LaunchedEffect` so flipping the flag re-scales the running video instead of re-creating the handle.

- **The header gate is orientation, not platform (2026-08-17)**: the migration above shipped with `val isMobilePortrait = true` hardcoded in all four screens — a "temporarily forced open so the layout can be judged on Desktop" that also **replaced the body of the portrait branch** with the landscape header. Android portrait therefore rendered the desktop header, and Android landscape/tablet lost the old layout entirely. The gate is now `val isPortrait = screenInfo.wDP < screenInfo.hDP` and nothing else: a portrait window (phone upright, or a narrow desktop window) gets the edge-to-edge artwork header, a landscape one gets the side-by-side header. `getPlatform()` no longer appears in Album/Playlist, and since 2026-09-23 not in ArtistScreen either — its `HazeProgressive` guard (about skiko, not layout) went with the switch to a `Modifier.blur` fade.
  - The old black `angledGradientBackground` layout is **deleted** from all four screens, since "not portrait" now means "landscape header" rather than "legacy layout". That also retired `PauseCircle`/`PlayCircle`/`Sensors`/`ElevatedButton` and, in ArtistScreen, `CollapsingToolbarParallaxEffect` plus 11 other imports.
  - **One boolean was answering two questions** — "use the immersive treatment" (palette background, row dividers, blurred top bar) and "which header". That is why forcing it to `true` broke the header while looking harmless: everything else it gated genuinely does apply to both orientations, so those conditions are simply gone.
  - Artist keeps two values on the orientation: frame `aspectRatio(1f)` vs the decoded banner's own aspect (2.4:1 until it decodes; a square bitmap left from portrait is ignored), and `ContentScale.FillWidth` vs `Crop`. *(Changed 2026-09-22: landscape was a fixed `height(hDP / 2)` strip that cropped the banner.)* The scrim is `fillMaxHeight(0.7f)` of the frame in both — measured off the frame, since the landscape frame no longer follows the window.

- **Liquid glass reaches Desktop, and its expect/actual is gone (2026-08-17)**: `io.github.kyant0:backdrop` is a **KMP** artifact declared in `commonMain.dependencies`, so Gradle had been resolving `backdrop-desktop` all along — the JVM side was simply never written. `LiquidGlass.jvm.kt` returned `Modifier` unchanged and `LiquidGlassContainer.jvm.kt` fell back to `clip(shape)`, so every glass surface on Desktop was a plain rounded box. Both actual pairs are now deleted: `PlatformBackdrop` is a `typealias` for Kyant's `LayerBackdrop` in commonMain, and the whole effect — `drawInteractiveGlass`, `GlassInteraction`, the observe-only press recogniser — is common code. The ~20 call sites keep the same names and did not change.
  - **The expect class was itself the blocker.** An `expect class` has no relationship to Kyant's `Backdrop`, so `drawBackdrop()` could not be called from commonMain and the 200-line effect was stuck in androidMain. Once the library exists on both targets the abstraction has nothing left to abstract, and dropping it is what let the code move. The alias survives only so call sites keep reading `PlatformBackdrop`.
  - Press/hold works with a mouse: it rides `pointerInput` + `awaitFirstDown`, not touch-specific APIs.
  - The landscape headers on Album/Playlist/LocalPlaylist now use glass for the back button and the like/search/`⋯` pill, matching portrait. Their buttons sit on the page background rather than on artwork, so the backdrop source is a `matchParentSize()` box carrying the palette colour — it takes part in no measurement and **must stay a sibling** of the buttons; nesting them inside the source is the render-feedback loop that crashes the RuntimeShader. The `[Shuffle][Play][Download]` cluster stays flat `White @12%` in both orientations, as it already was in portrait.
  - **The glass rim is `Highlight`, and its default is DIRECTIONAL — which is why small round buttons looked rimless.** `drawBackdrop`'s default is `highlight = { Highlight.Default }`, and `Highlight.Default` carries `HighlightStyle.Default`: a rim lit along a single direction (`angle = 45f`, `falloff = 1f`), not a rim around the outline. An elongated pill catches that sweep along its long edge and reads as glass; a 48dp circle catches a short arc of it and reads as nothing at all. `HighlightStyle.Plain` is the uniform one (`Color.White.copy(alpha = 0.38f)`, `BlendMode.Plus`). `liquidGlass`/`LiquidGlassContainer`/`LiquidGlassIconButton`/`drawInteractiveGlass` therefore take `highlight: Highlight = Highlight.Default` — the default keeps Kyant's own behaviour, so Android and the portrait branch are untouched. **The small round buttons pass `Highlight(width = 1.dp)`, NOT `Highlight.Plain` (corrected 2026-08-26).** `Plain` is uniform but reads as a flat wash; 1.dp is the smallest step that stays visible without looking like a plain border. Live examples: `AnalyticsScreen.kt:422` and the Apple Music player's Desktop dismiss button. Copy the value from the tree, not from this file's history.
    - Four builds were burned guessing at this before anyone read the library source. Things ruled out along the way, so nobody repeats them: hand-rolling the button as `Row + liquidGlass` (widening it to 96dp *does* make glass appear, because a longer edge catches the directional sweep — a symptom, not a fix), shrinking the lens radii through a `lensScale` parameter, moving the backdrop source between a `matchParentSize()` box and the content column, and painting the cover art into the source at low alpha (visible, but it silently changes the header design — do not). Swapping the back button and the pill between `TopStart`/`TopEnd` was the one useful experiment: the glass followed the *widget*, proving it was the surface's own geometry rather than its position.
  - **Proven on skiko, and Desktop is now ALWAYS glass (corrected 2026-08-26).** This entry originally read "unproven on skiko"; it has since shipped and runs. Desktop does not consult the `liquid_glass` setting at all — three call sites read `isLiquidGlassEnabled == TRUE || getPlatform() == Platform.Desktop` (`App.kt:427`, `App.kt:553`, `MiniPlayer.kt:179`), so the toggle is Android-only and Desktop is unconditionally on. New Desktop surfaces should therefore reach for `LiquidGlassIconButton`/`liquidGlass` by default rather than treating glass as the risky option. Kyant's desktop path does go through `SkikoRuntimeShader`, the same neighbourhood where haze 1.7.2's `HazeProgressive` throws `NoSuchMethodError` — that remains true of **haze**, not of Kyant's backdrop. *(Reversed 2026-10-26: the setting row now shows on Desktop and governs it like Android — `AppTheme` gets `isLiquidGlassEnabled == TRUE`, the Desktop capsule draws an opaque `surfaceContainer` pill when off, and the window Row and the sidebar record no backdrop. Added so the cost of glass could be measured by switching it off; the stored default is `FALSE`, so a Desktop that never touched the row now starts without glass.)*
  - `LiquidGlassAppBottomNavigationBar` still has an **empty** JVM actual — Desktop navigates with the rail, not the bottom bar. It is unrelated to the above and was not touched.

- **haze 1.7.2 → 2.0.0 (2026-09-24)**: 2.0 publishes no `haze-materials`; blur moved to **`haze-blur`** and the presets to **`haze-blur-materials`** (package `dev.chrisbanes.haze.blur.materials`, no opt-in). The mutable `Modifier.hazeEffect(state) { … }` DSL is gone — a `hazeEffect` still exists but is the generic custom-effect API (`factory, input, style`), so leftover calls fail as "no matching overload", not "unresolved". All 22 call sites are now `hazeBlur(HazeInput.Sources(hazeState), style)`: `Sources` is the 1:1 replacement for 1.x's state-based effect (`Backdrop` is only a native path behind an off-by-default flag, Android 37.2). The 13 tinted top bars share `barBlurStyle(tint, tintAlpha)` and the 9 plain ones `ultraThinBarStyle()`, both in `UIExt.kt`. Neither forces `blurEnabled`. haze blurs by default on Android 12+ and on Desktop, and everywhere else draws the style's `fallbackColorEffect`, which is set to the bar's own colour, opaque (2026-10-04).
  - **Do not force blur back on.** Below Android 12, haze blurs through RenderScript, which haze's own docs call experimental. That path still dies natively on haze 2.0 and 2.0.1, in `GrallocConsumer::lockNextBuffer`, while one blurred screen replaces another: Library into the four-tile screen above all, More albums too. In Sentry this is ANDROID-Q, -ND and -SE, on Android 10–11 only. A native crash leaves haze no chance to fall back. Forcing blur was why tapping Favorite / Followed / Most played / Downloaded crashed on a Realme 6 Pro running 2.2.0.
  - **A Style is compared by its recorded writes** (`HazeBlurStyle { }` records into a list; `RecordedHazeBlurStyle` has structural `equals`), so building one per recomposition is free — no `remember` needed.
  - `performanceMode` is left at `Default`, which is now `Adaptive` (downsamples under load); pass `HazePerformanceMode.Quality` if a bar looks softer than before.
  - haze 2.0 is built on Compose Multiplatform 1.12.0, i.e. skiko 0.150.x, and so is everything that moved with it. **That killed the Desktop tray at runtime, not at build time**: `composenativetray` 1.3.3 (the last release under `io.github.kdroidfilter`, built on Compose 1.10.3) calls `Image.encodeToData$default`, which skiko 0.150 no longer has — `NoSuchMethodError` on the first composition, from `Tray(…)` rendering its icon, while Gradle reports BUILD SUCCESSFUL. The tray moved to **`dev.nucleusframework:composenativetray` 2.1.6** (Compose 1.12.0), package `dev.nucleusframework.composenativetray`. `Tray`/`Item`/`Divider` kept their shape.
  - **`SingleInstanceManager` did not disappear in tray 2.0 — it moved to `dev.nucleusframework:nucleus.core-runtime`** (`dev.nucleusframework.core.runtime`). The tray pulls that artifact only into its RUNTIME variant, so it must be declared directly (`libs.nucleus.core.runtime`, on the `nucleus-notification` version) to compile against it. `isSingleInstance(onRestoreRequest = …)` still exists and still runs before `startKoin` (#2044); its callbacks now receive the restore-file `Path`. The README steers to `nucleusApplication { }` instead — do not take that route without moving `startKoin`, since that check would then run after Koin has already opened DataStore.

- **Settings grouped like Apple Music (2026-10-03)**: every section of `SettingScreen` is a `SettingGroup` (`ui/component/SettingItem.kt`): an uppercase header (the old headers' `labelMedium` size, Normal weight instead of Bold), the rows on one 20dp-rounded card, and an optional `footer` note under the card (SponsorBlock's intro, the import tools link). Rows separate themselves: `SettingItem` draws a hairline along its top, inset 16dp on the text's side, and the card clips the first row's away (it cannot paint over it: the card is translucent, alpha 0.5), so a row hidden by a condition never leaves a stray line at the top. The card is `surfaceContainer` (`surfaceContainerHigh` read too heavy), except on a light Desktop, whose panel already is `surfaceContainer`; there it is `surfaceContainerLowest` (white). The equalizer, delay and reverb panels inside it step up to `surfaceContainerHigh` so they stay a surface of their own. The proxy rows and the crossfade rows, which were LazyColumn items of their own, now sit inside the Content and Playback groups. `SettingItem` is used nowhere else, so its 16/12dp padding assumes a card; the equalizer, delay and reverb panels are inset 16dp to match.

- **Windows keeps the native title bar (2026-10-06)**: the custom title bar (undecorated + transparent window, 12dp corners, the 40dp `CustomTitleBar`) is now macOS-only. `DesktopApp.kt` gates it on `nativeTitleBar = !isMacOS`, the same path Linux has taken since 2026-09-22. That turned the Windows VM probe into dead code, so it is gone: it ran PowerShell `Get-CimInstance` (then `wmic`) inside `remember {}` during the first composition, so every Windows launch waited for it before the window appeared. The `-Dcompose.window.no-transparent` override went with it, since all it did was force Windows onto the native bar. `getScreenSizeInfo()` subtracts nothing there, because native decorations sit outside `containerSize`. The bar's colour is Windows' own: nothing tells DWM about the app's theme.

- **Right-to-left languages (2026-10-14, Hebrew/Arabic/Persian)**: an audit on a Hebrew device found three separate causes. The owner's rule behind all of them: in RTL only text flips, icons keep their shape and anything that shows which way time runs stays left-to-right.
  - **Hebrew moved folders.** Android 15+ with targetSdk ≥ 35 and the Desktop JDK report Hebrew/Indonesian as `he`/`id` (AOSP `BaseLocale.USE_NEW_ISO_LOCALE_CODES`); Android ≤ 14 still reports `iw`/`in`; Compose Resources match the folder name exactly. Crowdin exports `he`/`id`, so `values-he` and `values-id` are the live folders and `values-iw`/`values-in` serve old phones only — nothing updates them unless they are copied.
  - **Playback and time controls stay left-to-right** through `LeftToRight { }` (`extension/UIExt.kt`, a `LocalLayoutDirection.Ltr` provider): every player style's seek bar, times and transport (`AppleMusicPlaybackControls`, `SpotifyPlaybackControls`, `ExpressivePlaybackControls`, `PlayerControlLayout`), volume rows, the action rows under them, the three artwork pagers, the ±5 s video overlays, fullscreen lyrics/video, the mini player's progress, the Desktop capsule and mini-player window, the Analytics period navigator and the Wrapped reel. Before this, ⏩ sat on the left, every times row (`TextAlign.Left/Right` on weighted halves) collapsed onto its centre label, and M3E's `WavySeekBar` seeked backwards: its touch math is `x / width` while Material's indicator draws mirrored. A control of this kind added later needs the same wrapper. Text placed inside one (the Analytics date, Wrapped's cards) gets the reading direction provided back, or a right-to-left string comes out reordered.
  - **Compose lays every paragraph out in the layout's direction by default**: `TextStyle.resolveTextDirection` maps `TextDirection.Unspecified` to `Rtl`, not to the content. Latin titles and URLs therefore lost their punctuation order (".release", "/https://…") and titles mixing Latin with YouTube's localized "(עם …)" came out scrambled and clipped. `typo()` now sets `TextDirection.Content` plus `TextAlign.Right` in RTL layouts only — Content alone would also move Latin text to the left edge, since Compose aligns `Start` by the paragraph, unlike a TextView's gravity. Lyrics are unaffected: every lyric line sets its own direction and alignment.
  - Smaller fixes: `MoodCategoryCard` drew its badge at a fixed right corner, on top of the title in RTL; the equalizer's curve is drawn left-to-right, so its dB scale and frequency labels are kept left-to-right with it. The Glance `TurntableWidget` cannot pin a direction, and the launcher lays it out in the SYSTEM's direction rather than the app's language, so it reverses its own order when `Resources.getSystem()` is RTL.
  - Compose Desktop goes right-to-left too: `GlobalLayoutDirection` comes from `Locale.getDefault()` through AWT's `ComponentOrientation`.
  - Left as is: marquee titles scroll the RTL way for Latin text (`basicMarquee` follows the layout, not the text) — the owner declined changing it. Still open: the back button sits on the right while its arrow keeps pointing left. R8 renames every class it has (the Full build turns `AppStartMetrics` into `io.sentry.android.core.performance.g`); a reference to a missing class keeps its original name.

- **Dark theme is no longer AMOLED black (2026-10-15)**: `isAmoled` is a MaterialKolor parameter, not an app setting, and it is gone from both `rememberDynamicColorScheme` calls in `Theme.kt`; the Wallpaper scheme (`PlatformColorScheme.android.kt`) also stopped pinning `background`/`surface` to black by hand. In a dark scheme `isAmoled` swaps exactly four roles — `background`/`surface` to `#000`, `onBackground`/`onSurface` to `#FFF` — so the dark page is now MaterialKolor's tone 6 (about `#131313`, tinted by the seed) and `typo()` titles, which read `onBackground`, are tone 90 instead of pure white. Both calls change together: in the dark theme the immersive screens reuse the main scheme, so changing only one splits them by theme.
  - **Never hardcode `Color.Black` as a page or bar colour; use `colorScheme.background`.** Four blacks only looked right because the page was black: the liquid-glass backdrop base in `App.kt`, the `SongSelectionTopAppBar` fill on the library dynamic playlists (now with `contentColor = onSurface`, since the bar defaults to white text), and the fill behind a loading chip in `InfiniteBorderAnimationView`. The cold-start `windowBackground` is `#131313`, the neutral grey at tone 6.
  - **The reverse bites too: a Material default sitting on a fixed-colour surface.** `NavigationRail` defaults to `surface`, which was black only under AMOLED, so on the pure-black Desktop window (`desktopWindowDark`) it turned into a seed-tinted grey strip. It is now `containerColor = Color.Transparent` and shows the window on Desktop and the page on tablets. Anything placed on a surface with a fixed colour (the Desktop window, the player, the Podcast page) must not take a theme surface role, whether passed explicitly or inherited as a default.
  - Black that stays on purpose: scrims, video and canvas letterboxes, fades over artwork, glass darkening, and the surfaces that are black by design — the Now Playing sheet with its Classic and Apple Music pages, fullscreen lyrics, the Podcast page, and the Desktop window frame (`desktopWindowDark`: the window takes the extreme, mirroring pure white in the light theme).

- **Desktop sidebar replaces the rail (2026-10-22)**: on Desktop (`isDesktopShell`) the window's left edge is `DesktopSidebar` (`ui/component/DesktopSidebar.kt`), a second rounded `desktopPanel` beside the content panel, after Spotify's Your Library. Tablets keep `AppNavigationRail`. Navigation (Home, Mix, Analytics, Search) sits on top; Library leaves the navigation because the "Your library" header IS the Library tab (same `selectTab`, same `BottomNavScreen.Library.ordinal`). Under it: Favorite / Downloaded / Most Played pinned (counts from `getLibraryOverview()`), then local playlists, saved playlists, saved albums, followed artists and favourite podcasts as one list (`LibrarySidebarViewModel`, five Room flows `combine`d), with chips per kind (a chip shows only while its kind has items), an inline search, and Recents / Alphabetical sort. It folds to 72dp (icons and covers only) from 280dp, persisted as the DataStore string `desktop_sidebar_collapsed` through the generic `getString`/`putString`, so core was not touched. The playing row is matched by the queue's `playlistId` (`LOCAL_PLAYLIST_ID + id` for local playlists, `browseId` for albums, `podcastId` for podcasts); the pinned collections queue with a null id and are never marked. That makes FOUR components carrying the tab list (bottom bar, rail, glass bar, sidebar): a new tab goes into all four.
  - **The capsule player lives in a Box around sidebar + content panel, not in the panel.** It centres on everything left of Now Playing, and with the sidebar open and Now Playing showing the panel is narrower than the capsule (~770dp), so inside the panel it lost its right-hand buttons. Its glass source (`layerBackdrop(backdrop)`) is recorded on the Row holding sidebar and panel for the same reason: recorded on the panel alone, the part of the capsule over the sidebar refracted nothing and flickered. Tablets keep the capsule and the source in the panel, beside the rail.
  - **Now Playing's width is taken by hand: `(Row width − 80dp) × 0.35`, read from the Row's own constraints in a `layout {}`, not `fillMaxWidth(0.35f)`.** In a Row a fractional fill takes its share of the width LEFT after the unweighted siblings, so it was always 35% of what the 80dp `NavigationRail` left (80dp is `NavigationRailItemWidth` = `NavigationRailCollapsedTokens.NarrowContainerWidth` in the pinned material3; the 96dp `ContainerWidth` token is not what the rail uses). Next to the sidebar it shrank to ~27% and resized whenever the sidebar folded; with the rail and sidebar moved into the weighted Box it would have grown to 35% of the whole Row. Desktop takes another 8dp off because its 8dp spacer is gone (the content panel's own padding is the gap), so the card keeps its exact size. Do not use `LocalWindowInfo.containerSize`: it is not the Row's width.

- **Desktop frame governor: one frame budget for every window (2026-10-26)**: a SimpMusic left running on Desktop kept the fans going all day, on all three OSes. skiko capped nothing. macOS and Linux ran with `skiko.vsync.enabled=false` (the display-change freeze workaround, since removed — see the correction below), and skiko 0.150's refresh-rate frame limiter (`skiko.vsync.framelimit.fallback.enabled`) only covers vsync that is ON but unsupported, so `MetalRedrawer` (no `vSyncer`) and `LinuxOpenGLRedrawer` (`limitFramesIfNeeded` skipped) drew as fast as the GPU allowed whenever anything animated. Windows waits for vsync and so drew at the display rate all day. All three redrawers stop only when `layer.isShowing` is false, i.e. a window hidden to the tray; a minimized window still counts as shown. Re-enabling vsync is not an option: `DisplayLinkThrottler.mm` still waits on `lockWhenCondition:1` with no timeout in 0.150. `DesktopFrameGovernor` (`composeApp/jvmMain`) now decides for every window at once: focused → the display's refresh rate (no pacing of its own on Windows, where vsync already does it), on screen but unfocused → 30 fps, every window minimized or hidden or the app hidden with ⌘H → infinite animations wait.
  - **The hook is `InfiniteAnimationPolicy`, carried by the coroutine context.** Compose consults it before every frame of an animation that never ends (`rememberInfiniteTransition`, `infiniteRepeatable` specs, `basicMarquee(iterations = Int.MAX_VALUE)`). The state-based `Window` builds its `ComposeWindow(coroutineContext = rememberCoroutineScope().coroutineContext)`, so a policy placed in the context of `awaitApplication` reaches every window, the mini player included, without changing a single `Window` call. That is all `governedApplication` is: `application` with `runBlocking(DesktopFrameGovernor)`. Window state comes from one Toolkit-level `AWTEventListener` (window, window-state, focus and component events; resizes ignored) plus an `AppHiddenListener` for ⌘H.
  - **A loop that redraws every frame while something plays must take its frames from `withInfiniteAnimationFrameNanos`/`Millis`, not `withFrameNanos`**, or it slips past the governor. Converted: LyricsView's smooth playhead, the Apple Music lyric strip's sweep, Wrapped's reel timer. One-shot `withFrameNanos { }` waits (UIExt scroll helpers) stay as they are. On Android nothing installs a policy, so these behave exactly as before.
  - **Off screen, the player stops working for pictures too**: `AppOnScreen` (`core/domain`, beside `LiveStreamRegistry`) is the one switch, written only by the governor. The handler's position tick drops from 50 ms to 1 s (SponsorBlock can then skip up to a second late, the watch-time pings, the 5 s position save and the scrobbler are unaffected); every mpv handle that carries video gets `vid=no` and `auto` back on return (`MpvPlayer.setVideoSuspended`, applied by the adapter on change and in `applyPlaybackLevels()` for handles created meanwhile); a canvas (video-only) is paused instead, because a handle left with no track would end its file. Not rendering mpv frames is not a substitute: vo_libmpv's `flip_page` waits up to 200 ms per frame for a render that never comes, which stalls video instead of idling it.
  - The governor starts as on screen and unfocused, not off screen, so a missed window event costs 30 fps rather than freezing every animation in the app. The refresh rate is AWT's `displayMode.refreshRate`, 60 when the display reports none.

  - **Correction, same day: the governor alone did not cap the frame rate.** Skiko's FPS counter (`skiko.fps.enabled=true`, now set for dev runs in `desktopApp/build.gradle.kts`) showed 300–700 fps on Linux on 60/75 Hz monitors, and ~300 fps while MINIMIZED: anything that is not an infinite animation (finite animations, state writes) still drew uncapped with vsync off. Vsync is therefore back on everywhere, macOS included (`runDesktopApp` no longer touches `skiko.vsync.enabled`; skiko 0.150's macOS DisplayLinkThrottler wait still has no timeout, so watch for a freeze on display changes there); on Linux, dragging the window between a 60 Hz and a 75 Hz monitor did not freeze (CMP-9725 / CMP-10019 did not reproduce), the frame rate follows the monitor (60 / 75 fps), and a window covered by another one drops to ~1 fps, which the compositor does by itself.
