# Home, Browse, Library and downloads

Notes on Home sections, the Home backdrop and Create button, and the Browse page, the Library cards and auto playlists, Smart downloads, and the launch banners with their app links. Moved from the changelog in `CLAUDE.md`; each entry keeps its original date. Add to this file by the Auto-Update Rule in `CLAUDE.md`.

- **"More" on home sections, and a generic Browse page (2026-09-19)**: a home section that carries a `moreContentButton` now shows a More button, and its title opens the same place — measured on live responses, the title run's endpoint is identical to the button's (only `clickTrackingParams` differ), and a section without the button has no title endpoint either. The endpoint lands on `HomeItem.moreEndpoint` (`browseId`, `params`, `pageType`), read in `HomeParser`.
  - **Route by where the endpoint points, never by guessing from the id.** YouTube states the page type on the endpoint itself (`browseEndpointContextMusicConfig.pageType`): Explore's "Trending" More carries `MUSIC_PAGE_TYPE_PLAYLIST`. `navigateToMoreEndpoint` (in `AdapterItems.kt`) sends album/audiobook, playlist, artist/user-channel and podcast pages to their existing screens (`PlaylistRepositoryImpl` adds the `VL` prefix itself), and everything without a page type — the `FEmusic_*` ids: `listen_again`, `library_landing`, `moods_and_genres`, `new_releases_videos`… — to the new `BrowseDestination`. `params` travel verbatim, still URL-encoded (`ggMEgAKgAw%3D%3D`); ytmusicapi and Metrolist send them that way too.
  - **The Browse page copies Metrolist's `YouTubeBrowseScreen`**: `YouTube.browse()` in the scraper went from two shelf kinds to Metrolist's four — grid, carousel (two-row items, list rows and podcast episodes; immersive carousels arrive as carousels via `@JsonNames`), music shelf and playlist shelf — plus mood buttons (`musicNavigationButtonRenderer`), which is all `FEmusic_moods_and_genres` holds; each opens `MoodDestination(params)` from its own endpoint. Everything is flattened into one grid with `distinctBy { id }`, section titles dropped, and **no paging** — Metrolist's browse screens do not page either.
  - **Home's card dispatch is now `HomeContentCard`**, shared by Home's rows and the Browse grid, so an item opens and plays the same in both. It decides the card from which id is set and draws a wide thumbnail as a video card, so `YTItem.toHomeContent()` (in `Mapping.kt`) writes 544×544 for songs and 1280×720 for videos to say which.
  - **Justified rows, not a grid** — every thumbnail in a row is the same height, each card keeps its own shape (square, video 16:9), and the number of cards per row follows the shapes in it; `justifyRows()` in `BrowseScreen.kt` packs greedily toward a 180dp thumbnail and sizes each card to fill the row exactly (subtracting the cards' own 20dp padding, so the thumbnails — not the cards — come out equal). The shape comes from `Content.homeCardAspectRatio()`, which mirrors `HomeContentCard`'s dispatch. The cards take `fillMaxWidth` (default `false`, so Home/Library/Artist/Album are unchanged): `fillMaxWidth()` plus the card's own aspect ratio instead of the fixed 160dp / 284.5dp. Two grid attempts came first and both read as scattered: fixed-size cards in stretched `GridCells.Adaptive` cells with videos spanning two left a hole beside every card and a card-wide hole after every video; cards filling one cell each left videos squashed into a square cell's width. `LazyVerticalGrid` cannot vary the column count per row, which is the whole requirement once cards keep their own shapes.
  - It wears Mix for you's background: the artwork-tinted ambient glow (from the page's first item) and the bar that is transparent at the top and frosted once scrolled. The grid's top gap is `contentPadding`, not a spacer item, because the glow parks once item 0 has scrolled by — with a spacer as item 0 it parks after ~64dp, while most of the glow is still on screen.
  - **The two sections the app builds itself at the bottom of Home (issue #2461)** come from `FEmusic_new_releases` through `parseNewRelease`, not from `FEmusic_home`, so they needed their own wiring: `YouTube.newRelease()` now keeps each shelf's own More endpoint (`ExplorePage.releasedMoreEndpoint` from the first shelf, `musicVideoMoreEndpoint` from the last — the same shelves the two lists are read from), and `parseNewRelease` puts them on the two sections. The video one leads to `FEmusic_new_releases_videos`, a 100-item grid with no continuation, i.e. the whole list. **Signed out, the page has no album shelf** (measured 2026-09-19 in VN, US and GB, and `FEmusic_new_releases_albums` answers 404 there) — a signed-in session still gets one first, which is why "New releases" shows up for the owner. Measuring only anonymously led to the wrong conclusion that albums were gone; `parseNewRelease` now simply drops a section with no contents, which covers the signed-out case.
  - **The album shelf's More leads to a dead page.** It points at `FEmusic_new_releases_albums`, which 404s for every client tried on 2026-09-19 — the app's own 1.20260304 web client, YouTube Music's current 1.20260915.14.00, signed out in VN/US, and the owner's signed-in session. It has been failing since at least **2026-05-29**, when ArchiveTune (commit `da4f838a`) added a fallback for `newReleaseAlbums` throwing `ClientRequestException`; a Metrolist #1383 comment from 2026-02-06 already reports ArchiveTune's New Releases not working when signed in. Metrolist still calls it and shows an empty screen. `parseNewRelease` therefore drops that one id (`takeUnless`) — the plumbing stays, so the button returns by itself if YouTube ever points the shelf somewhere live. ArchiveTune's fallback chain (no account → `FEmusic_new_releases` → Explore) yields nothing in VN today either: signed out, neither page has an album shelf.
  - `getAlbumMore` also calls `YouTube.browse()` and reads the FIRST section. The artist-discography page is a single grid, so that is unchanged — but a page that ever puts another shelf kind above its grid would now hand `getAlbumMore` that shelf instead.
  - `BrowseViewModel` is a new Koin `viewModel {}` definition, and Koin definitions are the global state the Compose Hot Reload entry in `build-and-tooling.md` says CHR cannot rebuild — restart `hotRunJvm` before opening the Browse page after pulling this in.

- **"Liked songs" section on the artist page (2026-09-23, issue #2524)**: a section shaped like Spotify desktop's, placed above Popular — a "Liked songs" heading, then a 48dp artist picture wearing the red liked heart beside "N songs" / "By <artist>" (plural `liked_songs_count`, written `%1$d`: the old unused `n_song` plural uses bare `%d`, which Compose Resources prints verbatim). Hidden while the count is zero; opening `LibraryDynamicPlaylistScreen` as the new `LibraryDynamicPlaylistType.ArtistLiked(channelId)` (route `artist_liked_<UC…>`). Liked only, not downloads: the row says "Liked songs" and downloads already have their own list. `DatabaseDao.getLikedSongsByArtist` is a Room **Flow** (unlike the paged `getLikedSongs`), so liking from the page updates the count at once; it matches the channel id as a quoted token inside the `artistId` JSON with the same `replace()` + `ESCAPE '\'` treatment as `deleteUnfollowedArtists` — verified against the owner's DB: 76/76 artists match a JSON-parsed count, and 23 of those ids contain `_`. The list is ordered like Favorites (`favoriteAt ?: REMOVED_SONG_DATE_TIME`), **not** in SQL: 57 of 72 liked songs there have a NULL `favoriteAt`. The row navigates with the route's `channelId`, the id the count was queried with.

- **Your library cards redesigned (2026-10-07)**: the four pastel tiles at the top of the Your library tab (hardcoded `Color(0xff…)` fills, black text, blind to the theme) became one wide Favorite card plus Followed / Most played / Downloaded cards, each fanning the artwork of its newest items (`SleeveFan` in `LibraryTilingBox.kt`: newest drawn last so it lands on top). An empty collection draws dashed empty sleeves in the same slots, so a new user sees the shapes waiting to be filled; a null overview (first read not landed) draws titles only, so a full library never flashes as empty.
  - Data is `CommonRepository.getLibraryOverview()`: COUNT + newest-thumbnail DAO Flows for liked songs, downloaded songs and followed artists, plus the existing most-played Flow (already `LIMIT 50`, so its size is the count). All are Flows, so a like, follow or finished download updates the card at once.
  - The card container is `libraryCardColor()` (formerly TasteCard's private `tasteCardColor()`, white on a light Desktop); the taste card went to the same 20dp radius and lost its elevation so the tab reads as one flat family.
  - Rejected by the owner on the way, do not bring back: Apple Music's category list ("ko phải library đẹp"), an icon inside a tinted rounded square ("AI slop"), and 2×2 cover mosaics (YouTube Music's style).

- **Home: Your daily discover hero, "Play all" and hover play buttons (2026-10-07)**: three Home changes, all driven by what YouTube's Home response actually declares (measured on a signed-in and an anonymous Home).
  - **What YouTube declares about each shelf.** `numItemsPerColumn: "4"` appears only on song-list shelves (Quick picks, Heard in Shorts, Trending songs for you), and `itemSize` is `COLLECTION_STYLE_ITEM_SIZE_MEDIUM` on every shelf, so it carries no information. The header button is "More" when it holds a `browseEndpoint` and "Play all" when it holds a `watchEndpoint`. The Play all endpoint has `videoId` + `params` and no `playlistId`, and `/next` turns it into a finite `TLGG…` queue with no continuation. `HomeParser` used to read only the browse form, so Play all was dropped. These now land on `HomeItem.itemsPerColumn` and `HomeItem.playAllEndpoint`, and every shelf header (`HomeSectionHeader`, plus Quick picks') shows Play all as a text button, the same as More.
  - **"Your daily discover" is ArchiveTune's hero carousel** (`HomeDiscoverSection` in `HomeSectionStyles.kt`, M3 `HorizontalCenteredHeroCarousel`, which the pinned material3 ships). It applies to any card shelf of songs only that has no More page and no `itemsPerColumn`.
    - It shows one large card with narrow neighbours, the title on the art over a `colorScheme.scrim` gradient in `ForceDarkContent`. Tapping a neighbour brings it to the middle, and tapping the middle card plays its radio.
    - The large card targets a FIXED 360dp (`HERO_TARGET_WIDTH`, capped at 0.74 of the row on phones) and the carousel is 320dp tall (2026-10-22). Material's `heroKeylineList` picks how many large items fit by comparing the row against that target, so a share of the row (the old 0.6 / 0.74) gave the same count on every window width; a fixed target makes a wider window show more large cards.
    - "Mixed for you" deliberately stays on square cards: mix covers print their own title ("My Mix 06", "Supermix") along the bottom, so a hero crops it and an overlay duplicates it.
  - **Spotify-style hover on Home cards** (`rememberCardHover` + `HoverPlayButton` in `AdapterItems.kt`): pointer hover or keyboard focus tints the card with `onSurface` and raises a `primary` / `onPrimary` play button onto the artwork. Phones never hover, so they are unchanged.
    - Songs and videos play exactly as a tap does.
    - Playlists and albums play `Content.playEndpoint` through `BaseViewModel.playFromEndpoint` (an `RD…` id is queued as a radio, anything else as a playlist). That endpoint is the card's own play target, read off `thumbnailOverlay…musicPlayButtonRenderer.playNavigationEndpoint`: songs get `RDAMVM…`, playlists `PL…`, albums `OLAK5u…`, and artists none.
    - App-built new-release albums carry their `OLAK…` id. A playlist card without a target plays by its id.
  - **Do not copy how Vivi and ArchiveTune pick their special sections.** Both match the section title text ("cover" and "remix", a translated "community"). That breaks per language; our own Quick picks title match already fails in French ("Sélection rapide" vs "Sélection Rapide").

- **Launch banners from the remote config (2026-10-10)**: Home can show image-only promo banners, at most one per launch, defined by a `promos` array in the same `remote-config.json` that already carries the TIDAL credentials. Each entry is `id` (required: names the banner), `image` (language code → portrait banner URL; a missing or blank language falls back to `en`, and the code is the BCP 47 tag's first part, since Android's `Locale.language` still says `in`/`iw` for Indonesian/Hebrew), `link` (a `simpmusic://` deep link, routed through the same `App.kt` router as web and widget links, or an `https://` page opened with `openUrl`; an entry with any other link is skipped, since a tap could not act on it — one check, `isAppLinkAvailable(link, …)` in `utils/AppLinks.kt`), and optional `minVersion` / `requires` (only `local_tracking` is understood; an unknown requirement hides the entry from that build). Entries decode one by one, so one written with a wrong type drops alone — but a JSON syntax error anywhere in the file still fails the whole file, TIDAL included. Model in `core/domain/.../model/promo/Promo.kt`, selection in `utils/PromoSelection.kt` (pure, tested in `jvmTest`), UI in `ui/component/PromoBanner.kt`: the picture fills a width capped at 320dp in portrait and 360dp in landscape (less only when a 9:16 picture would pass 80% of the window height), and its own shape sets the height — no fixed frame; the owner rejected the old 9:16 box as inconsistent. It has no placeholder: the square holder made the frame square around a portrait picture on Desktop; tap to open the link, and only the Wrapped glass X closes it — the owner asked that a tap outside and Back do nothing.
  - **Each banner once per app version, one per launch, in the config's order.** `promo_shown` holds the app version on its first line and the ids shown in that version after it, so a new version starts the line over. A launch takes the first eligible banner not shown yet; closing or tapping it counts, stepping aside for anything does not, so a later launch offers it again.
  - **The picture is just an `AsyncImage` in the banner's dialog** — Coil loads it like any other image (disk cache first, the network otherwise, through the 24-hour TTL interceptor). There is no prefetch and no cache-only check: an earlier version prefetched pictures and refused any not already on disk, a leftover from when the banner was decided the moment Home opened, and the owner rejected it ("coil giải quyết"). A picture that fails to load closes the banner without counting it, so a later launch tries again; offline with the picture never loaded, that means the dialog opens and closes at once. `CommonRepositoryImpl` stores the raw `promos` block in DataStore after each config fetch (`"[]"` when the block is gone, which ends a campaign), and the decision reads whatever block is saved when its turn comes — often this launch's own fetch.
  - **It waits its turn and never shares the screen.** Once per launch, Home waits for its open counter, 1 s for its own launch dialogs (review, share lyrics, blog, Kotlin Footguns) to settle, then for the update check started at launch, however long it takes (`checkForUpdate()` raises `isCheckingUpdate` before its coroutine starts and always lowers it on completion, so the flag can neither be missed nor stick). The decided banner draws only after 400 ms in which nothing has blocked it: another dialog (Home's own, the log-in alert, and everything `App.kt` raises — update dialog, both notification-permission prompts, the sleep timer — folded into `LocalAppDialogOpen`), Now Playing (`LocalNowPlayingOpen`), or Home not being in front — RESUMED on Android (not mid-transition to another tab, not behind a system prompt), merely STARTED on Desktop (window showing): a Desktop window opened from a terminal or an IDE may start without focus, and the click that focuses it would count as the user starting, so a RESUMED gate there would never let the banner through. The 400 ms belongs to the banner (`promoClearFor` holds the banner it cleared), so it always starts at the decision: nothing left over from before the banner arrived can let it through early, and the update dialog, raised a frame after its check ends, gets there first.
  - **Never once the user is busy.** `App.kt` sets `LocalUserStarted` on the first press or wheel scroll anywhere in its `Scaffold` (watched in `PointerEventPass.Initial`, nothing consumed — mini player and nav bar included; dialogs and sheets are windows or layers of their own, so closing one does not count) or when Now Playing opens. Before the banner's turn, that puts it off to a later launch, uncounted; so does leaving Home before the decision finishes. The "decided" flag is `rememberSaveable` (a rotation is not a new launch) and is set at the START of the attempt: a value written while Home is being left is never saved.
  - **The update dialog no longer offers a release this build is already at or ahead of** (`VersionManager.isBehind` → `isNewerRelease`): a tag is offered unless it names this very version (leading `v` stripped) or this build's numbers are higher. It used to compare tags for inequality, which told a dev or beta build to "update" down to the latest release, and told every F-Droid-channel user to update on every launch: that channel's tag has no leading `v`. Numbers are compared part by part with any `-suffix` dropped, so a hotfix tag (`v1.0.1-hf`, a pattern this repo has shipped) has the same numbers as the release it fixes and is still offered by its different name, and a final release is offered over its `-beta`.
  - **Dev builds read `remote-config-dev.json`** (`AppIdentity.isDevBuild`: `BuildConfig.DEBUG` on Android, `-Dsimpmusic.dev=true` set by desktopApp's JavaExec tasks on Desktop) and keep the promo block and the shown list under `_dev` keys, so testing on a Desktop that also has the release installed leaves the release's banners untouched. The TIDAL keys are NOT split — a Desktop dev run writes the same DataStore as the installed release — so the dev file must carry the same TIDAL values as the release file.
  - **Links the banners use**: `simpmusic://analytics` (the receipt), `simpmusic://library?tab=<chip>`, where `<chip>` is `LibraryChipType.toStringValue()` (`wrapped` for Wrapped), and `simpmusic://taste` (the AI taste card: Library on Your library, given a link of its own so the code can tell that the card needs local tracking, which `library?tab=your_library` cannot say). The tab travels as `SharedViewModel.requestLibraryTab()`, which `LibraryScreen` applies and clears; `LibraryViewModel` no longer lets its saved chip, read asynchronously at startup, overwrite one picked meanwhile. **Whether a link's screen exists for this user is decided in ONE place, `utils/AppLinks.kt` `isAppLinkAvailable()`**, used by both the router and banner selection so they cannot disagree: Analytics, the Wrapped chip and `taste` need local tracking, the YouTube playlists chip needs a YouTube sign-in, and a path the router does not open (`APP_LINK_PATHS`, to be kept in step with the router's `when`) is never available. The router toasts "not supported" for an unavailable link; a banner pointing at one is simply not shown — so the config needs no `requires` for any of this (`requires` remains for conditions a link cannot express). The router reads both settings BEFORE `setIntent(null)`, because clearing the intent changes the routing effect's key and the next frame cancels the effect wherever it is suspended, which would drop the navigation after the banner was already counted. These links push the destination like the widget's `simpmusic://library` always has, so the tab bar still highlights Home after one (the bars move their highlight only on a tap). Syncing the bars from `currentBackStackEntry` was tried and reverted on 2026-10-10: on the owner's Nothing phone the Home tab stopped responding, cause not pinned down — find it before trying again.
  - **Logs:** every step writes under the tag `Promo` at Info (the decision and why nothing was picked, put off because the user started, on screen, opened, closed, picture failed), so the Developer option log screen answers "why no banner" — the usual answer being `promo_shown` already listing the banner for this version.

- **"Cached" auto playlist in Library (2026-10-16, Android only)**: songs whose audio sits in the player cache in full and that are not downloaded — what plays offline without having been downloaded. A fourth small card beside Followed, Most played and Downloaded turns that row into a 2×2 grid on Android; Desktop keeps no song cache on disk (mpv streams) and keeps its single row of three. `CacheRepository` gained `getFullyCachedSongIds()` (audio keys only — the video stream is cached under a `MERGING_DATA_TYPE.VIDEO` key — and only those `isFullyCached`, so a track skipped halfway is left out) and `removeCachedSong()`; Desktop's stub returns nothing.
  - **Read on demand, never observed**: the player cache is no table, so both the card (`LibraryViewModel.refreshCachedPreview`) and the list (`LibraryDynamicPlaylistViewModel.getCachedSong`) read it each time their screen is shown, through the shared `loadCachedSongs`. A cached song whose row "clear listening history" swept has no metadata to show and drops out.
  - **There is no duplicate copy to clean.** A finished download already removes its player-cache copy (`playerCache.removeResource(id)` on `STATE_COMPLETED` in `DownloadUtils`); the bytes are only written to both caches while the download runs, because the download reads through a `CacheDataSource` on the player cache. Downloading from this list therefore costs no network, and the song moves to Downloaded by itself.
  - The ⋯ sheet takes `onRemoveFromCache`, which adds a "Remove from cache" row only when the sheet is opened from this list.

- **Smart downloads (2026-10-16, Android only, issue #2662)**: a Settings switch under "Download songs you like" keeps the songs played most downloaded, 25, 50 or 100 of them (default 50; the count row only shows while the switch is on). It needs local tracking to be switched on, and stays switchable off without it so the songs can still be cleared. A pass is asked for on every `MainActivity.onStart` and when the switch or the count changes in Settings. It runs at most once a day (`smart_downloads_last_run` is stamped before the pass starts, and an in-flight pass blocks a second one) and only on an unmetered network (`isOnUnmeteredNetwork()`, expect/actual; Desktop answers false). Off such a network a Settings change resets the stamp to 0, so the next open on Wi-Fi runs it.
  - **Never from `SharedViewModel.init`.** The three Glance widgets inject that ViewModel in `provideGlance`, so it can be created with the app in the background, where the pass's `startService` (Media3 `sendAddDownload(foreground = false)`) throws. There is no background job for the same reason: Android 12+ refuses a download service started from the background.
  - **Score**: every play of the last 30 days in `playback_event` adds `min(1, listenedSecond / durationSecond)` (1 when the length is 0) × `0.5^(ageDays / 14)`; ties go to the most recent play. Summed in Kotlin over `SongPlaySample` rows whose `timestamp` is `LocalDateTime`, for the same reason as `PlaybackSample`.
  - **The marker is a column that already existed**: a smart song carries `song.category = SongEntity.SMART_DOWNLOAD`, and a downloaded song without it is the user's and is never touched. This only holds because nothing reads `category` (the mappers just copy it) and nothing rewrites a whole `song` row (`insertSong` is IGNORE). **Reading `category` for something else, or adding a REPLACE/`@Upsert` on `song`, silently breaks Smart downloads.**
  - **One pass, in order**: drop the marker from marked songs no longer downloaded, and from liked songs while liked songs auto-download; rank; keep only rows YouTube confirms as songs (`MusicVideoType.isAudio`) that are not live, so videos, podcasts and unknown types never qualify; mark and `downloadTrack` the top N not downloaded yet; then evict FIFO by `downloadedAt` (in-flight downloads sort last, and a song in today's top N is never evicted) with `removeDownload` first and the unmark second, so a process death in between leaves a mark the next pass clears. Switching off removes every marked song; a liked one (with auto-download on) only loses the marker.
  - **Album and playlist download states are deliberately not asked.** Opening an album whose tracks are all downloaded marks the album downloaded (`AlbumViewModel`'s download-state collector; `PlaylistViewModel` does the same), so reading "in a downloaded album or playlist" as the user's claim took smart songs the user never claimed and kept them past N for good.
  - **Nothing in a pass may crash the app.** The pass and the clear catch everything but cancellation and log it, so a `startService` refused after the app went to the background just ends the pass. `isOnUnmeteredNetwork()` reads a `SecurityException` from `getNetworkCapabilities` (b/163342798, the same guard WorkManager's `NetworkStateTracker` has) as off-Wi-Fi. The notification check falls back to notifying on a database error.
  - Smart songs post no per-song "downloaded" or "failed" notification: `MusicDownloadService.TerminalStateNotificationHelper` checks the marker first. The download service's progress notification still shows.

- **Home header draws YouTube's own backdrop (2026-10-20)**: the Home response carries a top-level `background.musicThumbnailRenderer`, one pre-blurred 1500×844 image that changes with the mood chip (signed out with no chip it was a dark aurora; signed in on "Relax", bright pool water). `BrowseResponse.background` already parsed it for Podcast pages. `getHomeData` now returns it as the third value of its `Triple`, and `HomeScreen` draws it behind the first shelf in both themes. Continuations carry no image, so `getHomeDataContinue` stays a `Pair`.
  - **The artwork tint stays underneath as the fallback.** A response without the image, the load itself and a failed load all show the old 25° gradient from the first card's dominant colour. A failed load drops the image and its overlay (`onError`), since the overlay alone would darken the fallback too.
  - **A page-coloured overlay always sits on the image**, 60% at the top left and rising to opaque along the tint's own 25° line. Some images are very bright, and fading with the bottom scrim alone left a flat horizontal band. The overlay takes `pageBackground`, so it lightens in the light theme and darkens in the dark one with no branch.

- **Create button on Home (2026-10-22, issue #2596)**: a "+" (`CreateActions` in `ui/component/CreateSheet.kt`, after Spotify's Create) opens a sheet with Local playlist and Listen Together. Local playlist opens `CreateLocalPlaylistSheet`, the name sheet that used to be written inline in `LibraryScreen` and now also serves Library's create tile. On Home, Notifications moved into the avatar menu and Listen Together into the sheet, and the live-room dot (`LiveRoomDot`, shared with `ListenTogetherIconButton`) moved onto the "+". With liquid glass on, "+" and Settings share one glass pill, like the like/search/more pill on the playlist screens. With glass off, "+" is a grey circle with a border and Settings stays a plain icon. The chips' end padding dropped from 148 to 100 dp (two end buttons). Library has no "+": only Home got one (an earlier "+" there was removed at the owner's request).
  - **Add to queue on an empty queue starts playing it.** That is the whole of #2596: no separate "new queue" action. A "Queue" entry in the Create sheet (an empty queue behind a placeholder mini player) was built and removed the same day as useless. `addToQueueBlock` returns null for an empty or null queue, so Endless queue cannot block the first Add to queue, and `addToQueueLabel()` (now `@Composable`, reading the queue) labels the button "Create a new queue and add to play" there (`create_new_queue_and_play`), in every sheet that has it.
  - **Appending into an emptied player must point it at item 0.** Both adapters (`CrossfadeExoPlayerAdapter`, `MpvPlayerAdapter`) keep their own playlist, and `clearMediaItems()` leaves `localCurrentMediaItemIndex` at -1. `addMediaItem` never moved it, so the handler's `prepare()` on the first appended item loaded nothing, and Add to queue into an empty queue did nothing on either platform. `pointAtFirstItemIfUnset()` in both `addMediaItem` overloads gives ExoPlayer's own behaviour.
